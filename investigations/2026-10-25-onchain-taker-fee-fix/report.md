# План исправления onchain истории на VPS и NAS

Основная работа выполняется на VPS `sun`: изменение кода, проверки, скачивание Telonex, подготовка исправленных Parquet, восстановление 20 сентября, публикация и отправка на NAS. Переносить весь архив на Mac не требуется. Отдельная операция на NAS `pizza` — свежий ZFS-снимок перед заменой файлов; он требует административного доступа. Сейчас такой доступ с VPS не настроен, поэтому снимок выполняет владелец через SSH с Mac или консоль NAS.

Это план исполнения от 25 октября 2026 года. Изменения кода, остановка сервисов и запись в основной архив ещё не выполнены. Основание — [результаты проверки трёх игр](../2026-10-25-onchain-taker-fee-history/report.md).

Незакрытый день не переписывать. Даты начала остаются прежними; менять ONCHAIN_START_DATE для запуска ремонта не требуется.

## Проверенное окружение

На VPS есть Docker, Python 3, uv, rsync и Git. В окружении `/root/work/esports-trader/.venv` установлены httpx, pyarrow, duckdb и python-dotenv. TELONEX_API_KEY уже задан в `/root/work/esports-trader/.env`; скрипт должен читать только нужный ключ из этого файла и не выводить значения окружения. Ключ не копируем в collector, команды shell, Dockerfile или журналы.

Node, Corepack и Yarn на хосте отсутствуют. Устанавливать их глобально для этого ремонта не требуется. Постоянный TypeScript-код проверяется внутри контейнера Node 24; текущий Dockerfile уже устанавливает зависимости, выполняет yarn check и собирает dist.

Во время проверки VPS имел 8 CPU и 16 ГБ RAM, около 9 ГБ доступной памяти и около 330 ГБ свободного диска. Перед запуском эти показатели проверить заново. Современные onchain-файлы всего затронутого периода ещё находятся на VPS. Полные тесты и Docker-сборку с yarn check запускать в окне без live-карт согласно правилам проекта. Миграцию выполнять последовательно, без нескольких DuckDB-процессов; сетевую загрузку ограничить четырьмя запросами одновременно. Для отдельных тестовых и ремонтных контейнеров использовать 2 CPU, 3 ГБ памяти и отсутствие swap. Эти ограничения docker run не ограничивают автоматически Docker BuildKit.

На момент проверки серверный collector находился на commit `90854a9`, а локальный checkout Mac был на `be53688`. Исходной версией разработки считаем актуальный checkout VPS, после повторной проверки HEAD и чистоты файлов. Автоматический pull, reset, замена checkout или push в этот план не входят.

## Каталог запуска

Документ и одноразовые скрипты хранятся в workspace, а не в продуктовом репозитории. На VPS использовать:

```text
/root/work/betting_workspace/investigations/2026-10-25-onchain-taker-fee-fix/
  report.md
  work/
    scripts/
    run-<UTC>/
      inventory/
      source-metadata/
      telonex/
      staged/
      rpc-rebuild/
      backup/
      verification/
      progress.jsonl
```

Структуру создаём на VPS перед исполнением; локальная версия документа сама на сервер не синхронизируется. Скрипты должны принимать явные пути входа и выхода. Исследовательские скрипты с путями `/Volumes/polymarket` не запускать на VPS без адаптации.

Каталог запуска находится вне `.onchain`: стартовая очистка collector удаляет оттуда временные каталоги. Backup, Telonex-входы и подготовленные файлы должны переживать рестарт сервисов. Манифесты, исходные хеши, число строк и каждый завершённый этап записывать в progress.jsonl, чтобы продолжение не повторяло уже проверенную работу.

## Этап 1 Подготовить код на VPS

В `/root/work/polymarket-collector` исправить общий декодер. Он должен сохранять taker-агрегат, связывать его с конкретным OrdersMatched и распределять комиссию между соответствующими maker fills. Учитывать несколько OrdersMatched в одной транзакции, оба exchange-контракта, направления buy и sell, прямую сделку и операции с двумя исходами. Одинаковое исполнение в двух outcome-проекциях получает одинаковую комиссию.

Внести явную новую версию декодера для исправленной семантики. Старый repair v1→v2 оставить самостоятельной миграцией: он исправляет taker_asset_id и не предназначен для комиссии. Простое увеличение decoderVersion не пересчитывает готовую историю.

Исправить определение диапазона UTC-дня. Константу 94 154 038 нельзя считать началом существования V2: есть подтверждённый успешный V2 receipt от 17 сентября в более раннем блоке. Для восстановления 20 сентября диапазон должен включать весь нужный UTC-день.

Подготовить отдельный режим пересчёта одного дня в изолированные выходные архивы и state. Этот режим нужен для 20 сентября и не должен сбрасывать рабочий ledger или запускать перерасчёт всех дней.

Проверить fixtures с реальными receipt, в том числе несколько maker fills с нулевым maker fee и ненулевой комиссией taker. Полный yarn check должен пройти. Проверить идемпотентность миграции и отказ от публикации при неизвестной комиссии, дубликате ключа или конфликтующих исходных данных.

Собрать новый образ на VPS. Сначала записать фактический image ID работающего onchain и сохранить его под отдельным тегом для отката. Сборка через `docker compose build archive-dota` обновляет общий образ, но сама не перезапускает сервис archive-dota. Новый образ пометить отдельным тегом и записать его ID и commit.

**Результат этапа:** проверенный образ и скрипты ремонта. Работающие сервисы пока используют прежний код.

## Этап 2 Подготовить историю без замены основных файлов

На VPS запустить одноразовую Python-миграцию через существующее окружение esports-trader с uv run --no-sync. Она не меняет код или зависимости esports-trader. Новые интерфейсы prepare, verify, publish и resume предстоит реализовать; текущий исследовательский preview не является готовой командой публикации.

Заново снять инвентаризацию трёх архивов. Зафиксировать исходные Parquet, manifest, receipt и хеши. Дни с готовыми manifest брать из их списка файлов; 18–19 сентября Dota и LoL включить отдельно как старый импорт. Пустые файлы не требуют API-запроса за комиссией.

Выполнить подготовку fee-only для всей затронутой истории. Телонекс-файлы сохранять в каталоге запуска с собственными SHA-256. Соединять строки по `(tx_hash, log_index, asset_id)`. Для старых строк искать данные по фактическому block_timestamp_us и соседним UTC-дням. Не найденные ключи проверять по RPC. Неразрешённая строка блокирует публикацию дня; нулевая подстановка недопустима.

Подготовленные Parquet должны иметь те же строки, их порядок, схему и значения всех колонок, кроме taker_fee. Дополнительные исполнения Telonex не добавлять автоматически на этом этапе. Старое taker_asset_id и прежнюю раскладку строк по файлам не менять в fee-only миграции; их исправление требует отдельной проверки.

**Результат этапа:** полная проверенная версия комиссии в `staged/`, без изменения основных архивов.

## Этап 3 Восстановить 20 сентября отдельно

На VPS запустить исправленный однодневный RPC-пересчёт Dota и LoL. Использовать отдельные архивные корни и отдельный onchain state внутри `rpc-rebuild/`. Из рабочих архивов брать нужные metadata; рабочий ledger и manifest остаются нетронутыми. CS2 в этот день не участвует.

Сравнить полный результат с прежним днём: все прежние исполнения должны сохраниться, а новые строки иметь подтверждённые blockchain-ключи и относиться к восстанавливаемому диапазону. Расхождение вне комиссии, подтверждённых новых строк и связанных с ними технических метаданных исследовать до публикации. Если изолированный пересчёт меняет набор охватываемых рынков, сначала зафиксировать причину и конечный список токенов.

Для 20 сентября итогом будет полный исправленный RPC-день, а не поверх него ещё один fee-only файл. Подготовить согласованные manifest, сведения о диапазоне, версии и происхождении. Перенос необходимого ledger и каталогов из изолированного пересчёта оформить явным импортом новых записей; прежний ledger сохраняется и не переписывается вслепую. После старта collector должен распознавать опубликованный день как готовый.

**Результат этапа:** проверенная замена 20 сентября и отчёт о количестве добавленных исполнений.

## Этап 4 Подготовить резервные копии и короткое окно публикации

После долгой подготовки, непосредственно перед заменой, на VPS остановить только onchain и ship:

```bash
cd /root/work/polymarket-collector
docker compose stop onchain ship
```

Дождаться освобождения их блокировок. Получить стабильную резервную копию заменяемых Parquet, manifest, receipt, onchain ledger и необходимых каталогов состояния. Использовать список файлов операции, а не копирование всего архива книг. Проверить backup по записанным хешам. Повторно сравнить текущие исходные файлы с хешами этапа подготовки; если они изменились, этот день подготовить заново.

На NAS владелец создаёт свежий рекурсивный ZFS-снимок `tank/polymarket` с именем `before-onchain-repair-<UTC>` и проверяет его наличие. Сам snapshot выполняется на NAS; управляющую SSH-сессию сейчас удобнее открыть с Mac. Проверено, что SSH с Mac работает, но sudo требует интерактивную аутентификацию. С VPS обычный SSH на pizza сейчас завершается ошибкой проверки ключа хоста. Отключать проверку хоста ради ремонта не следует.

Доступ ship уже использует закреплённый ключ NAS и ограничен `rrsync -wo -no-del`. Через него можно перезаписывать файлы и выполнять предусмотренную rsync-проверку; команду zfs snapshot этот ключ выполнять не может. Если нужен запуск буквально всех управляющих команд с VPS, до этого этапа отдельно настроить проверенный административный доступ на NAS с правом создания нужного снимка. Такой доступ для самого переноса данных не требуется.

**Условие перехода:** рабочие onchain и ship остановлены, источник не изменился, VPS-backup проверен и свежий NAS snapshot существует. Archive-dota, archive-lol, archive-cs2, compact и live-трейдер продолжают работу.

## Этап 5 Опубликовать исправленные файлы и включить новый onchain

На VPS миграция публикует подготовленные файлы по дням с журналом состояния операции. Для каждого дня сначала меняются проверенные Parquet, затем последним публикуется новый manifest с актуальными размером, числом строк, границами времени, SHA-256 и версией преобразования. Сохранить происхождение fee из Telonex и входные хеши. Повторный запуск должен узнавать уже завершённый день.

18–19 сентября остаются старым импортом без фиктивного ready-manifest. Для них записать отдельный repair manifest со списком исходных и новых файлов и хешей; не присваивать доказательство полной blockchain-покрытости, которого эта операция не создаёт.

Проверить все опубликованные файлы на VPS. Для обычного fee-only дня число, ключи и порядок строк и все остальные поля должны совпадать с backup. Для 20 сентября действуют отдельные проверки полного пересчёта.

Запустить только onchain из нового образа:

```bash
docker compose up -d --no-deps --force-recreate onchain
docker compose logs --since 5m onchain
```

Проверить image ID, версию декодера, состояние дня 20 сентября и обычный проход сервиса. Простое `restart` не заменяет контейнер новым образом. Сборку образа к этому моменту уже завершили; во время публикации её не выполняем.

## Этап 6 Синхронизировать NAS с VPS

На VPS включить ship с временно отключённым prune, не меняя постоянное значение в .env:

```bash
SHIP_PRUNE=false docker compose up -d --no-deps --force-recreate ship
docker compose logs --since 5m ship
```

Ship увидит новые байты manifest, признает прежние receipt неактуальными, повторно отправит изменённые дни и проверит содержимое NAS через rsync checksum. После успеха появятся новые receipt, соответствующие новым manifest. У ship нет штатного флага одного прохода; запускать его как обычный сервис и ждать завершения нужных дней, а не рассчитывать на несуществующий --once.

Для 18–19 сентября выполнить отдельную отправку с VPS тем же закреплённым SSH-ключом и точным списком изменённых файлов. Использовать checksum-сравнение и ремонтную запись доставки с хешами, не включать удаление файлов NAS. Подготовить файл списка и скрипт заранее, чтобы не формировать широкий шаблон путей вручную. Штатный ship этих legacy-дней сам не обнаружит.

После обоих проходов на VPS сопоставить локальные SHA-256 с manifest и выполнить полную rsync checksum-проверку списка затронутых файлов на NAS. Проверить количество файлов и актуальность всех новых receipt. Проверка не требует выдавать ship административный доступ или читать NAS через его SSH-ключ.

Когда итог подтверждён, вернуть ship к настройке prune из исходной .env:

```bash
docker compose up -d --no-deps --force-recreate ship
```

Успешная доставка не является причиной удалять резервную копию операции. Backup и snapshot сохраняются до отдельного решения после проверки следующих закрытых дней.

## Этап 7 Проверить данные и потребителей

На VPS проверить текущую работу onchain и ship и сопоставить комиссии новой небольшой выборки с Telonex или receipt. Из-за сохранения идентификаторов fee-only дни не требуют пересчёта WS↔onchain reconcile. Для 20 сентября пересчитать reconcile, поскольку добавился набор onchain-исполнений; прежний отчёт сохранить в backup.

Архивную taker_fee текущий бэктест не читает, поэтому сама исправленная комиссия не требует пересчёта его результатов. Добавленные исполнения 20 сентября меняют вход бэктеста. На машине следующего запуска адресно инвалидировать кэши этого дня и затронутых рынков. Если reader не умеет адресную инвалидацию, согласовать конкретный более широкий сброс до выполнения; автоматически удалять весь общий кэш не нужно.

На VPS сохранить итог: исходный и новый commit и image ID, количество переписанных файлов и комиссий по играм, число добавленных строк 20 сентября, контрольные суммы, список receipt и ссылку на NAS snapshot. Отчёт после выполнения синхронизировать в локальный workspace для чтения.

## Откат

При ошибке публикации остановить onchain и ship, восстановить затронутые файлы и согласованные manifest из VPS-backup по журналу операции. Из onchain state откатывать только записи и каталоги, затронутые этой операцией. Если сервис уже успел обработать другие дни после запуска, сохранить их новые записи; полную старую копию state поверх текущей не класть. Для отката кода выбрать записанный прежний image ID через временный Compose override для onchain; не менять общий latest-тег вслепую и не пересоздавать все сервисы.

Если часть новых файлов уже ушла на NAS, после восстановления согласованного источника повторно доставить прежние версии с checksum-проверкой. При использовании ZFS snapshot сначала восстановить нужные файлы в отдельный каталог; рекурсивный rollback всего dataset может отменить новые данные других дней и не является автоматическим шагом этой операции.

Исправленный общий декодер работает на VPS. Все выбранные закрытые дни имеют проверенную комиссию; неразрешённых ключей нет. Обычные исторические строки сохранили остальные поля, 20 сентября восстановлено с подтверждёнными дополнительными исполнениями. На NAS совпадают затронутые файлы, современные receipt актуальны, legacy-дни имеют отдельное подтверждение доставки. Onchain и ship работают, prune возвращён к исходной настройке, backup и snapshot доступны.

Основания для команд Docker: [ресурсные ограничения контейнеров](https://docs.docker.com/engine/containers/resource_constraints/) и [многоэтапная сборка](https://docs.docker.com/build/building/multi-stage/). Пути, сервисы и ограничения ship проверены по актуальным Compose, Dockerfile и исходному коду collector на 25 октября 2026 года.
