## Где растут затраты

`src/backtest/run.py:682` хранит `all_quote_events` за все предыдущие карты. После каждой карты строки 735–738 сохраняют результаты и fills, добавляют новые quote events и передают весь накопленный список в writer.

`src/backtest/results.py:337–342` делает:

```python
frame = pd.DataFrame([asdict(event) for event in events])
write_parquet(frame, report_dir / QUOTE_EVENTS_FILENAME)
```

Таким образом на карте 370 заново создаются словари и DataFrame для карт 1–370. При сопоставимом числе событий на карту суммарная работа по сериализации растёт квадратично с количеством карт: 1 + 2 + ... + N. Одна и та же ранняя карта сериализуется сотни раз.

`read_quote_events_checkpoint` (`results.py:345–358`) при resume снова загружает полный DataFrame и превращает его в Python-объекты. Поэтому рестарт с coalescing fix сохраняет и наследует прежний объём телеметрии.

## Память Mac

- RAM: 32 GiB; CPU: 12 логических ядер.
- Swap used: 7 163 MiB в одном из снимков.
- seed0 `vmmap`: physical footprint 4.3 GiB, peak 4.8 GiB.
- seed7: footprint 2.9 GiB, peak 4.7 GiB.
- seed2: footprint 2.9 GiB, peak 4.8 GiB.

Это три выборочных процесса; пики не обязательно совпадают по времени. Уже такой масштаб плохо совместим с 12 процессами и остальными приложениями на 32 GiB. `ps RSS` показывает только резидентную часть и существенно занижает впечатление о памяти сида при активном сжатии/выгрузке.

Десятисекундный замер vm_stat: swap-in около 3.19 MiB/s, swap-out 0, логический объём compressions около 2 759 MiB/s, decompressions около 2 207 MiB/s. Последние два числа — счётчики страниц × размер страницы / время, не скорость диска и не объём уникальных данных. Они показывают активную работу с памятью в этом окне.

У QuoteEvent нет slots. В небольшом измерении один экземпляр занимал 48 bytes плюс 208 bytes словаря, без учёта объектов значений. На 2.5 млн строк это уже около 640 MB только на оболочки; asdict, pandas и Arrow добавляют временные представления.

`pmset -g therm` не сообщил зарегистрированных thermal/performance warnings. Причина пользовательского наблюдения высокого kernel_task этим не доказана. Apple объясняет, что одна из функций kernel_task — ограничивать доступный CPU при температурных условиях: https://support.apple.com/en-asia/102172 . Не следует приравнивать kernel_task к замене RAM или делать вывод о перегреве только по его присутствию.

## Малый диагностический benchmark writer

100 000 реальных QuoteEvent из текущего checkpoint, отдельный временный процесс, запись во временную папку, параллельно продолжаются 12 сидов:

| Вариант | Построение, с | Всего, с | CPU, с |
| --- | ---: | ---: | ---: |
| Текущий asdict → pandas → parquet | 0.794 | 0.862 | 0.607 |
| Именованные поля через tuple → pandas → parquet | 0.221 | 0.267 | 0.256 |
| Типизированные колонки Arrow → parquet | 0.184 | 0.211 | 0.142 |

Arrow-таблицы, прочитанные из первого и последнего файлов, точно равны после удаления metadata. Получено около 4.1× на этой операции. Это один пробный замер, а не обещание ускорения всего validation в 4.1×; не проверяет полноценную миграцию writer/reader/resume.

## Рекомендуемый порядок изменений

1. **Сохранение по картам с ограниченной памятью.** Писать атомарные порции результатов/fills/events для завершённой карты, затем освобождать её объекты. Resume читает список завершённых карт и необходимые агрегаты, а не миллионы старых событий. Компактация итогового совместимого parquet — один раз, потоково, без восстановления всех QuoteEvent. Summary также не должен снова материализовать всю телеметрию. Начать с сохранения всех значений и исходного порядка событий.
2. **Убрать промежуточные dict/pandas в writer.** Типизированные Arrow batches дают отдельный измеримый выигрыш и ограничивают временные копии. Slots могут дополнительно уменьшить оболочки объектов, но сами по себе не исправят рост списка и полные перезаписи.
3. **Компактная аналитика no_quote.** Сейчас это 94% строк. Для обычного прогона достаточно согласованных счётчиков/интервалов блокировки, с полным trace в диагностическом режиме. События заявок, fills, cancel acknowledgements и резервов сохранить: wallet/reserve расчёты используют их. Это изменение схемы аналитики, его следует отделить от первого шага без изменения значений.
4. **Проверить 6/8/12 workers на одном фиксированном наборе карт после исправлений.** Выбирать по полному времени, peak footprint и memory pressure. Сейчас уменьшение параллелизма может облегчить давление памяти, но сравнительный throughput 6/8/12 в этой диагностике не измерялся. BACKTEST_REPLAY_LOAD_WORKERS=1 можно проверить для загрузки; текущий batch содержит одну карту/две книги, поэтому реальный fan-out в логах 2, несмотря на configured cap 8. Это второстепенно относительно 84% времени после framework.
5. **Дальше профилировать сам replay.** Имеются несколько core.step на один evaluate через ClockUpdate/BookUpdate/SignalUpdate/BudgetUpdate/Wake; возможная оптимизация требует отдельного профиля и проверки одинакового порядка событий. Общий core и cadence следует сохранить при оптимизации обвязки.

Критерии проверки первого изменения: одинаковые сделки/заявки/времена/PNL/резервы и значения телеметрии на одних картах и seeds; resume после прерывания без пропусков/дубликатов; одинаковая скорость начала и хвоста прогона; ограниченная память на каждом из 12 workers. Время считать от начала одной карты до начала следующей, включая сохранение.

## Отдельная ошибка аналитики

`src/backtest/results.py:112–122`, `_count_gate_seconds`, продолжает считать одну строку no_quote за одну секунду. После перехода с 1 Hz на событийный cadence это количество событий, а не секунды. Текущие gate_seconds нельзя интерпретировать как длительность. Например, у карты 8837869969 одна категория other равна 19 763. Нужны реальные интервалы/длительности либо честно переименованные счётчики; простой множитель 0.1 также неверен при непостоянной частоте.

## Реалистичные ожидания

Если мысленно убрать весь измеренный этап после framework, на данной выборке потолок прямого выигрыша примерно 30.65 / 4.98 = 6.2×. Освобождение памяти может дополнительно ускорить сам replay, но это ещё не измерено. Ускорение всего прогона в 10× возможно рассматривать как цель, а не обещание.

454 карты × 12 seeds = 5 448 симуляций. При идеальном параллелизме 12 workers полный validation за минуту требует в среднем 60 / 454 = 0.132 s на одну карту/seed, включая загрузку и запись. Текущая наблюдаемая фаза framework около 5 s/карта уже соответствует примерно 38 минутам для 454 карт на worker, если считать её репрезентативной; это иллюстрация масштаба, не прогноз оставшегося времени. Для минутного цикла разработки разумен фиксированный небольшой smoke-набор, полный multi-seed validation остаётся отдельной проверкой.
