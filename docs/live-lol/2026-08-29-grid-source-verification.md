7 секунд меньше, чем `source_lag_seconds = 10` в `model.json`. Правка не

**Первый замер дал −25 секунд и был неверным.** Компаратор считал время
livestats как `wall − spawn_wall` и не вычитал паузы, а на карте CBLOL была
пауза 32 секунды. Пайплайн обучения вычитает паузы через `assign_game_times`.
Компаратор теперь использует ту же функцию.

Перекрёстная проверка пауз. На карте LEC:

- livestats насчитал одну паузу 99.5 секунды;
- якорь часов GRID `occurred_at − clock_seconds` прыгнул ровно на 100 секунд.

Два независимых источника согласились. На CBLOL якорь GRID не двигался вовсе:
разброс 0 на 165 фреймах.

Поиск сдвига по кривой золота ненадёжен: дно плоское, и он даёт +22 вместо
+7. Причина в смещении net worth ниже. Меряем по смертям.

### Пункт 2: одна настоящая проблема

**GRID `NetWorth` и livestats `totalGold` — разные величины.**

Из сырого GRID-фрейма видно: `NetWorth = Money + LoadoutValue`. Проверено на
игроках: 365 + 1700 = 2065, 1381 + 2150 = 3531. Это текущее нерастраченное
золото плюс стоимость предметов.

livestats `totalGold` — всё заработанное с начала карты. Разница это варды,
зелья и потери на перепродаже.

Отношение GRID к livestats на 1566 парах при сдвиге +7:

| Сторона | p10 | медиана | p90 |
|---|---|---|---|
| blue | 0.947 | **0.957** | 0.976 |
| red | 0.925 | **0.949** | 0.958 |

GRID ниже на 4–5%, и стороны смещены по-разному. Разница между сторонами и
даёт смещение главной фичи:

| Величина | p10 | медиана | p90 |
|---|---|---|---|
| `nw_adv` GRID минус livestats | −15 | **+133** | +382 |
| `nw_adv` сам сигнал livestats | −1033 | −145 | +446 |

**Знак `nw_adv` расходится на 15% сэмплов (242 из 1566).**

`xp_adv` на правильном сдвиге ведёт себя лучше: медиана расхождения 0,
p10/p90 равны −480 и +480 при собственном размахе сигнала −980..+1280.
Знак расходится на 13%. Ранее я приводил для `xp_adv` расхождение 680 —
это была цифра на неверном сдвиге +22.

Остальные фичи:

| Фича | Расхождение |
|---|---|
| `deaths_blue`, `deaths_red` | совпадают точно |
| `top1_ratio_over_rest` | 1.8% |
| `top1_ratio_over_total` | 1.3% |
| `xp_adv` | медиана 0, но p10/p90 равны −480/+480, знак расходится на 13% |

### Побочные находки

**Формулы top1 расходятся.** Модель LoL обучена на `top1 / сумма`
(`lol/livestats_frames.py:397`). Live-путь Dota считает `top1 / (сумма − top1)`
(`shared/utils/top_players.py`). На спавне 0.20 против 0.25. Это баг в плане,
а не в данных.

**GRID не шлёт `increaseLevel`, пока на карте не случился первый level-up.**
`_player_from_row` тогда ставит всем уровень 1. Это верно до первого
level-up, но `xp_adv` в ранней игре шумит. У GRID есть сырой
`ExperiencePoints` на игрока, который точнее лестницы уровней. Модель обучена
на лестнице.

**Разрежённость GRID.** На CBLOL 167 сэмплов за 715 секунд, то есть один раз
в 4.3 секунды. livestats даёт около 3 Гц. Часть разброса выше это разрежённость,
но медианное смещение +133 ею не объясняется: симметричный шум дал бы медиану
около нуля.

## Как повторить: пункты 1 и 2


Нужна одна живая карта, записанная с обоих источников одновременно.

### Шаг 1. Найти живую карту

```
make run F=scripts/record_lol_dual_feed.py
```

Скрипт печатает два списка: live-события Polymarket с `gridSeriesId` и
live-игры lolesports. Нужна карта, которая есть в обоих.

### Шаг 2. Записать

```
make run F=scripts/record_lol_dual_feed.py ARGS="<slug>"
```

Пример: `ARGS="lol-navi-gx-2026-08-29"`.

Скрипт сам находит `gridSeriesId` по slug и `esportsGameId` по кодам команд.
Если совпадений несколько, добавь `--esports-game-id <id>`.

Пишет в `data/lol_dual_feed/<slug>-<stamp>/`:

- `grid.jsonl` — сырые фреймы widget socket с меткой получения;
- `livestats.jsonl` — сырые ответы окна с меткой получения;
- `target.json` — что именно записано.

Останавливать Ctrl-C. **Нужно минимум 8 минут игрового времени.** Меньше — и
поиск сдвига не наберёт пар.

Записывать надо карту, которая только начинается. Если карта уже идёт
десятую минуту, livestats всё равно догонит по окнам, а GRID начнёт с
текущего состояния. Для поиска сдвига этого хватит, но чем длиннее общий
отрезок, тем надёжнее.

### Шаг 3. Сравнить

```
make run F=scripts/compare_lol_grid_livestats.py ARGS="data/lol_dual_feed/<run>"
```

Скрипт делает три вещи:

1. Приводит фреймы GRID к тем же 12 фичам, что читает модель. Секунда
   считается как в `grid_feed.py`: часы scoreboard плюс возраст метки минус
   `feed_delay` таблицы.
2. Приводит окна livestats к фичам через готовый `features_from_sides`.
   Ноль часов — первый фрейм с ненулевым золотом, как в обучении.
3. Ищет сдвиг от −120 до +120 секунд, который лучше всего совмещает кривые
   золота синей стороны. Затем печатает расхождение по каждой фиче.

## Как читать результат

### Сдвиг часов

```
best offset: grid_second = livestats_second +N
```

- `N` близко к нулю: часы совпадают, правка не нужна.
- `N` постоянный и заметный: добавляем константу в GRID-путь LoL.
- Соседние сдвиги дают почти такую же ошибку: кривая пологая, одного матча
  мало. Записываем второй матч.

Ниже печатаются сдвиги в окне ±3 секунды. Если их стоимость близка, оценка
неточная.

### Расхождение фич

Для каждой фичи выводится медиана `|grid − livestats|` и та же величина в
процентах от livestats.

Ожидания:

- `deaths_blue`, `deaths_red` — должны совпадать точно. Расхождение значит,
  что сдвиг подобран неверно.
- `blue_nw`, `red_nw` — livestats берёт `totalGold` команды, GRID суммирует
  `NetWorth` игроков. Небольшая разница нормальна. Больше 3% — разбираемся.
- `xp_adv` — обе стороны считаются по `LOL_LEVEL_XP` от уровня. Должны
  совпадать почти точно.

### Отдельная проверка: две формулы top1

Скрипт печатает обе:

- `top1_ratio_over_rest` — `top1 / (сумма − top1)`, правило
  `shared/utils/top_players.py`, которое использует live-путь Dota;
- `top1_ratio_over_total` — `top1 / сумма`, правило
  `lol/livestats_frames.py:features_from_sides`, на котором обучена модель
  LoL.

**Это уже найденное расхождение, а не гипотеза.** Модель LoL обучена на
`top1 / сумма`. Если в LoL-ветке live-пути переиспользовать
`build_top_player_features`, две из двенадцати фич поедут.

Правка в стадию 5 плана: `build_top_player_features` получает правило игры,
или LoL-ветка считает ratio своей функцией. Решаем после того, как увидим
цифры.

## Что делаем с результатом

| Результат | Действие |
|---|---|
| Сдвиг около нуля, фичи сходятся | План идёт как написан, плюс правка top1 ratio |
| Сдвиг постоянный | Добавляем константу в GRID-путь LoL, план идёт дальше |
| Сдвиг плавает по матчу | GRID нужен свой якорь нуля. Стадия 5 растёт |
| Золото расходится больше 3% | Модель на GRID кормить нельзя без переобучения. План пересматриваем |

Записанный `grid.jsonl` в любом случае идёт в
`tests/lol_grid_widget_fixtures.py` как фикстура стадии 0.
