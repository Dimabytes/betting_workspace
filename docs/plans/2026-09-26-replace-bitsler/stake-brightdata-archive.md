## Итог попытки

### Почему каталог Stake не получен

1. Без Custom Headers & Cookies Stake отвечал 400. Apollo на Stake блокирует POST как CSRF, если `Content-Type` «простой». Web Unlocker по умолчанию сам собирает заголовки и отбрасывает заголовки клиента.
2. Режим Custom Headers & Cookies включён в 10:04:43Z: у зоны `cust_head: 1`. После этого все 7 ответов Stake — 403. Bright Data считает 403 блокировкой (`http_status`) и выбрасывает тело ответа.
3. Ни в одном ответе `x-brd-debug` нет `used_req_headers`. Bright Data не передал Stake `Content-Type` ни через direct API, ни через native proxy.
4. Страна peer не влияет на результат. 403 пришёл с `au`, `fi`, `jp` и `es`. Stake не блокирует Финляндию и Японию.
5. Способ подключения тоже не влияет: direct API и native proxy дали одинаковый 403.
6. Ошибку 407 в вызовах 12–14 вызвал неверный логин прошлого пробника. Правильный логин: `brd-customer-hl_d92d83fc-zone-web_unlocker1`, порт `44445`. Пароль зоны отдаёт `GET /zone/passwords?zone=web_unlocker1`. С этим логином вызовы 15–17 прошли авторизацию.

Дата: 26 сентября 2026 года. Проект на VPS: `/root/work/esports-trader`. Разработка идёт прямо на VPS, в этом checkout на `main` (раздел 7).

Пробник потратил 6 из 10 вызовов Web Unlocker. Следующий вызов только после включения этой опции.

### 1. Результат, который нужен

Трейдер самостоятельно находит Oddin ID для текущих и будущих матчей Dota 2, получает игровые данные напрямую из Disir и продолжает работать после закрытия Bitsler. Домашний компьютер и ручное обновление Chrome/cookies не требуются.

Целевой бюджет — $0 в месяц в пределах бесплатной квоты Bright Data. Платный расход не включать автоматически. Если позже понадобится резерв до $1, сначала проверить условия пополнения и явно настроить предел расходов.

Схема:

```text
                           один редкий запрос на весь каталог
VPS → Bright Data Web Unlocker → Stake GraphQL → постоянный локальный кэш
                                                   ↓
Polymarket + Steam/GRID → сопоставление команд → od:match:N
                                                   ↓
                         VPS → Disir HTTP + WebSocket → текущий выбор фида
```

Полная замена включает каталог, токен Disir, переподключение после разрыва WebSocket и действующие диагностические команды. Смена каталога сама по себе не гарантирует, что Oddin покрывает каждый рынок Polymarket.

### 2. Исходные данные и ограничения

#### Что установлено по локальному коду

- `src/trader/source_picker.py` тоже использует `widget_config`; замена токена должна охватить probe и основной поток.
- `src/trader/cadence.py` запускает общий discovery Dota/LoL раз в 30 секунд. Медленный запрос Bright Data нельзя вставлять в этот общий синхронный проход.
- `src/trader/collector_sidecars.py` уже предоставляет `event_id`, `event_slug`, имена исходов и номер карты. В `FreshSidecar` нет времени начала: план не предполагает наличие несуществующего поля расписания.

#### Что известно из предыдущих проверок пользователя

Stake отдавал список через `POST https://stake.com/_api/graphql` без логина. Нужные поля: `extId`, `status`, `provider`, полные имена из `teams`. `type: active` включает live и ещё не начавшиеся матчи. В статусе самой карточки `active` означает «ещё не начался».

Disir доступен по `https://api-disir.oddin.gg/main/disir/query`. Его GraphQL ID — base64 от `match/od:match:N`. Есть операторский токен Stake, отдельный от Bright Data API key. Расшифровка уже реализована, net worth доступен, XP отсутствует.

Это входные данные для первого проверочного этапа, а не подтверждение того, что новый путь уже работает.

### 4. Архитектура и постоянное состояние

Добавить один фоновой загрузчик каталога в процесс WalletHost, которому назначена Dota. Он получает запросы на обновление от discovery, выполняет сетевой запрос независимо и публикует неизменяемый снимок каталога. Общий discovery продолжает читать готовый снимок с прежним интервалом.

Не создавать отдельный сетевой сервис, универсальный framework провайдеров или браузерный демон. Использовать существующий HTTP-клиент проекта; для Bright Data direct API не требуется добавлять SDK.

Предлагаемые границы модулей:

| Файл | Ответственность |
|---|---|
| `src/trader/stake_catalog.py` — новый | Bright Data transport для одного Stake-запроса, валидация ответа, перевод карточек в внутренние записи |
| `src/trader/oddin_catalog.py` — новый | Фоновое обновление, объединение запросов от discovery, политика повторов и жизненный цикл |
| `src/trader/oddin_catalog_store.py` — новый | SQLite-кэш, сохранение бюджета, состояния ожидания и права на одно обновление |
| `src/trader/oddin_types.py` | Небольшие frozen dataclass для карточки, снимка каталога и запроса на поиск |
| `src/trader/oddin_discovery.py` | Сопоставление карточек с известными командами и проверка неоднозначностей через Disir |
| `src/trader/discovery.py`, `wallet_host.py` | Чтение кэша, запросы обновления для неизвестных серий, запуск и завершение загрузчика |
| `src/trader/oddin_client.py`, `oddin_live_feed.py` | Прямой Disir без Bitsler; операторский токен и переподключение |

Использовать SQLite из стандартной библиотеки: кэш и бюджет требуют согласованных записей и сохранения после рестарта. Предлагаемый host-путь: `data/oddin_catalog/catalog.sqlite3`. Подключить один host-каталог к live/paper как `/app/data/oddin_catalog`, чтобы смена режима торговли не обнуляла бюджет.

Хранить:

- Карточки: Oddin ID, home/away, нормализованный статус, время первого/последнего наблюдения, наличие в последнем полном ответе.
- Метаданные: версия схемы, время последней успешной загрузки, время последней попытки и причина ошибки.
- Связь `Polymarket event_id → Oddin ID`, подтверждённую командами и Disir; карты одной серии используют эту связь совместно.
- Состояние поиска по `event_id`: последние попытки, число срочных повторов, причина следующего обновления.
- Счётчики всех исходящих попыток по UTC-дню и календарному месяцу. Провайдерский биллинг может считать меньше; локальный счётчик намеренно консервативный.

Обновление и резервирование бюджета делать короткими транзакциями. Сетевой вызов выполнять вне транзакции. Для нескольких процессов использовать сохраняемое право на один запрос с ограниченным сроком: перед передачей права повторно проверить бюджет и время предыдущего запроса. Падение процесса не должно навсегда блокировать каталог или обнулять расход.

HTTP/GraphQL-ошибка не заменяет рабочий кэш пустым. Валидный пустой список сохраняет отдельный факт «источник сейчас вернул ноль карточек»; старые ID остаются кандидатами с пометкой отсутствия в актуальном списке. Отсутствие карточки в Stake не равно завершению серии.

Не наблюдавшиеся карточки хранить до 48 часов как кандидатов для прямой проверки Disir. Уже используемый сессией ID не удалять во время её работы. Сохранять будущие карточки, которые продолжают присутствовать в каталоге. Старый статус `live` не использовать как доказательство того, что карта идёт сейчас.

### 5. Частота обновления и предел расходов

Начальные настройки:

| Настройка | Значение |
|---|---:|
| Фоновое обновление | 1 раз в 30 минут |
| Общий минимальный интервал между попытками | 60 секунд |
| Срочный повтор для уже начавшейся неизвестной серии | 1 раз в минуту, максимум 10 попыток на event_id |
| После исчерпания срочных повторов | Обычное фоновое обновление |
| Максимум одновременно выполняемых запросов | 1 |
| Timeout одного обращения к Bright Data | 60 секунд |
| Срок права на обновление при падении процесса | 90 секунд |
| Локальный дневной предел | 140 попыток |
| Локальный месячный предел | 4 500 попыток |
| Раннее предупреждение о месячном расходе | 4 000 попыток |

Правила:

1. При холодном старте читать диск и запускать обновление в фоне; на пустом кэше дождаться следующего обычного discovery после появления данных.
2. Для новой неизвестной серии из Polymarket запросить одно внеочередное обновление. Все неизвестные серии объединить в один полный запрос каталога.
3. Для будущей серии без live-признака не включать минутные повторы. Срочный режим запускать, когда Steam/GRID уже показывают нужную текущую карту, а подходящего Oddin ID нет.
4. Новый `condition_id` карты 2/3 не создаёт новый бюджет поиска: дедупликация по `event_id`, а не по рынку карты и не только по паре названий команд.
5. Когда ID известен и Disir отвечает, каталог ради статуса карты не запрашивать. Решения о свежести и текущей карте принимаются по Disir.
6. Не повторять запрос в каждом 30-секундном discovery. При сетевом отказе использовать увеличение паузы, например 1, 2, 5, 15, 30 минут, и учитывать `Retry-After`. Ошибки авторизации/конфигурации не расходовать минутными повторами.
7. Каждую внешнюю попытку учитывать до отправки, включая timeout, неуспех и повтор после аварии. Автоматические повторы HTTP-клиента не должны обходить счётчик.
8. Рестарт, переход live ↔ paper и параллельный пробник с VPS используют один счётчик. Локальные эксперименты с тем же аккаунтом учитывать отдельно и вычитать из свободного резерва.

Расчёт для одного запроса на полный каталог: 1 440 фоновых запросов за 30 дней, 1 488 за 31 день. До локального месячного лимита остаётся 3 060 / 3 012 попыток на срочные обновления и ошибки. Дневной предел 140 даёт максимум 4 340 за 31 день. Это ограничения предлагаемой реализации, а не гарантия наличия карточек.

Bright Data выдаёт новым аккаунтам общую квоту 5 000 кредитов каждый месяц; Web Unlocker расходует один кредит за запрос. Её также расходуют другие продукты аккаунта. Резерв 500 кредитов не заменяет контроль общей квоты. При исчерпании бесплатного лимита без внесённых средств API останавливается. [Условия бесплатной квоты](https://docs.brightdata.com/general/account/billing-and-pricing/free-tier)

При локальном лимите остановить только новые запросы каталога, оставить кэш и действующие Disir-подписки, вывести явную причину деградации. Настройки расписания и лимитов вынести в отдельную небольшую конфигурацию каталога; не расширять торговую конфигурацию произвольными полями.

### 6. Сопоставление матчей и полное удаление зависимости Bitsler

#### Привязка

- Переиспользовать `shared/utils/team_names.py` и текущие aliases. Сохранять проверку обеих команд и разворота сторон.
- Home/away не считать Radiant/Dire. Ориентацию текущей карты по-прежнему определять существующим Steam/GRID-путём и подтверждать данными Disir.
- Проверять stale-кандидата и неоднозначные совпадения через Disir. Старую карточку другой серии с такой же парой команд не выбирать только из-за совпадения имён.
- Перед допуском фида подтвердить ожидаемый номер карты, данные текущих команд и допустимую задержку. `probe_oddin_delay` должен сохранить чтение реального WebSocket-типа данных, а не доверять статусу Stake.
- Сохранять отдельно предварительно найденную карточку и фид, прошедший проверку готовности. Наличие ID не гарантирует net worth и задержку ≤61 секунды.
- Для кэша использовать отдельную запись каталога без выдуманных счёта серии и турнира. Не заполнять неизвестные данные фиктивными нулями ради старого `LiveMatch`.

#### Disir

1. Заменить `BITSLER_BRAND_TOKEN` на конфигурируемый `ODDIN_BRAND_TOKEN` со значением оператора Stake. Само значение перенести из имеющихся настроек/данных пользователя при реализации; в этот документ его не дублировать.
2. Сохранить `base64("match/" + oddin_match_id)`, `Origin: https://disir.oddin.gg`, HTTP и WS Disir. Bright Data участвует только в запросах каталога Stake.
3. Переименовать `bitsler_client` в нейтральный клиент Disir. Удалить Bitsler endpoints и обход `breadcrumbs/getMatch` из действующего Dota-пути.
4. После WS `complete` получать состояние непосредственно из Disir. Подтверждённое завершение закреплённой карты/серии завершает поток; переход к другой карте не должен перепривязать текущую сессию.
5. Timeout, пустой snapshot или закрытие сокета не считать завершением матча. Переподключаться с ограничением попыток; последовательность `complete` без полезных данных тоже должна расходовать лимит, чтобы не получился бесконечный цикл.
6. Сохранить текущую расшифровку и модель без XP, формат архивов, правила выбора фида и размеры ставок.

#### Скрипты и границы LoL

Обновить Dota watcher под нейтральное имя `watch_oddin_live.py`: выбор из кэша или прямой Oddin ID, без сетевого запроса к Bitsler. Обновить соответствующие тесты и примеры запуска.

`watch_bitsler_lol.py` импортирует общие Bitsler-функции. Не оставить сломанные импорты после очистки клиента. Для этого экспериментального watcher сохранить режим явного Oddin ID и убрать Bitsler discovery; отдельный каталог LoL в эту работу не включать. Рабочий LoL-трейдер остаётся GRID-only. Проверку совместимости операторского токена с экспериментальным LoL watcher выделить в отдельный результат, не выдавать её за проверку Dota.

Исторические логи и документы с упоминанием Bitsler сохранять. Финальная проверка должна искать активные сетевые обращения и импорты, а не требовать удаления слова Bitsler из всей истории репозитория.

### 7. Порядок реализации и проверки

#### Шаг A. Пробник и реальные fixtures

Выполнить этап 1. Добавить ограниченный диагностический сценарий, который печатает только список карточек, длительность, коды ошибок и результат проверки Disir. Зафиксировать выбранную зону и подтверждённую форму ответа. Все следующие шаги опираются на этот результат.

Промежуточный результат 26.09.2026, VPS, зона `web_unlocker1`:

| Вызов | Длительность | Итог |
|---|---:|---|
| POST GraphQL JSON | 57 с | Stake HTTP 400, GraphQL error |
| POST, повтор | 60 с | timeout на границе 60 с |
| POST, повтор | 60 с | timeout |
| POST | 53 с | Bright Data `http_status`, target 502, тело отброшено |
| POST | 111 с | Stake HTTP 400, текст ошибки сохранён |
| GET того же запроса | 69 с | тот же Stake HTTP 400 |

Текст ошибки Stake: операция заблокирована как CSRF. Нужен `Content-Type`, отличный от `application/x-www-form-urlencoded`, `multipart/form-data` и `text/plain`, либо непустой заголовок `x-apollo-operation-name` или `apollo-require-preflight`. Обычный Web Unlocker такие заголовки не передаёт. GET тоже простой запрос, поэтому CSRF срабатывает и на нём.

Каталог, fixtures и Disir на этом шаге ещё не получены. Следующий вызов — POST с `Content-Type: application/json` после включения Custom Headers & Cookies. Эта опция списывает кредит и за неуспешный запрос.

После включения опции, 26.09.2026:

| Вызов | Длительность | Итог |
|---|---:|---|
| POST + `Content-Type: application/json` | 79 с | peer `au`, Stake HTTP 403, Bright Data `http_status`, тело отброшено, `billed=true` |
| повтор | 16 с | снова peer `au`, тот же 403, `billed=true` |
| тот же POST, `country=ie` | 120 с | timeout, тела нет |

В `x-brd-debug` нет `used_req_headers`, поэтому передача `Content-Type` не подтверждена. Пользователь подтвердил, что `Content-Type` есть в pre-approved списке для `stake.com`, и разрешил ещё 10 вызовов. Таймаут пробника поднят до 240 с. Лимит попыток — 19.

Дополнительные вызовы после этого:

| Вызов | Длительность | Итог |
|---|---:|---|
| direct API, `country=fi`, `Content-Type` в JSON | 130 с | peer `fi`, Stake HTTP 403, тело отброшено, `used_req_headers` нет |
| то же плюс Origin, Referer, `x-operation-name` | 123 с | тот же 403 |
| прокси `brd.superproxy.io:44445` | 1 с | `407 Auth failed`, до Stake запрос не дошёл |
| прокси, пароль не в URL | 1 с | снова `407` |

Пробник остановлен на 14 из 19. Каталог и Disir ещё не получены. Direct API авторизуется ключом, но не показывает, что целевой `Content-Type` ушёл на Stake. Прокси, через который custom headers реально прикладываются к запросу, отклоняет пароль зоны из API.
