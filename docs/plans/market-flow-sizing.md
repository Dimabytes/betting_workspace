# Минутный размер входа по потоку тейкеров

## Результат

Для каждой Dota-карты измеряем поток тейкеров не чаще одного раза в 60 секунд.
Первый запрос запускается сразу после того, как рынок сопоставлен со Steam-
матчем. Каждый следующий Steam-тик использует значение из памяти и не делает
HTTP-запрос, пока минутный кеш не потребует обновления.

Размер BUY и решение `торгуем / пропускаем` могут измениться после очередного
минутного обновления. Внутри минуты все тики видят один и тот же sample.

Пользователь меняет только две настройки размера:

```python
MIN_CLIP_USDC = 10.0
MAX_CLIP_USDC = 200.0
```

Все долларовые лимиты fork и risk автоматически выводятся из
`MAX_CLIP_USDC`. Пользовательская конфигурация не содержит
`base_size_usdc`: это внутреннее производное значение.

## Правило расчёта размера

Размер BUY задаёт константа `LIQ_FLOW_MULT_PER_MIN`; её значение соответствует
5% от taker-notional в долларах за минуту:

```text
rate_per_min = taker_notional_usdc за последние 20 минут / 20
raw_clip     = LIQ_FLOW_MULT_PER_MIN * rate_per_min

если raw_clip < MIN_CLIP_USDC:
    карту не торгуем
иначе:
    clip_usdc = min(raw_clip, MAX_CLIP_USDC)
```

`MIN_CLIP_USDC` одновременно задаёт минимально разумный ордер и производный
порог потока. `MAX_CLIP_USDC` задаёт максимальный ордер и масштаб всех
долларовых ограничителей.

При значениях `$10 / $200`:

| Поток тейкеров | Сырой клип | Результат |
|---:|---:|---|
| `$164/мин` | `$8.20` | пропустить карту |
| `$200/мин` | `$10.00` | торговать по `$10` |
| `$453/мин` | `$22.65` | торговать по `$22.65` |
| `$2,000/мин` | `$100` | торговать по `$100` |
| `$4,000/мин` | `$200` | торговать по `$200` |
| `$10,000/мин` | `$500` | торговать по потолку `$200` |

`LIQ_FLOW_MULT_PER_MIN` и окно `1200` секунд — правила стратегии, а не ручки
масштаба. Из двух пользовательских значений автоматически следуют:

```text
минимальный flow = MIN_CLIP_USDC / LIQ_FLOW_MULT_PER_MIN
flow потолка     = MAX_CLIP_USDC / LIQ_FLOW_MULT_PER_MIN
```

## Когда обновляем поток

Обновление не привязано к horn. Оно начинается, как только `MatchWorker` уже
знает неизменяемый `conditionId`, то есть сразу после сопоставления sidecar со
Steam-матчем. Ждать `horn-60`, `horn-30` или первого разрешённого входа не надо.

Каждый запрос получает завершённое скользящее окно:

```text
anchor = целая Unix-секунда в момент начала запроса
window = [anchor - 1200, anchor)
```

На attach и на каждом следующем Steam-событии worker вызывает
`_maybe_refresh_flow(now)`. Этот метод работает как минутный TTL-кеш:

1. Если попытка уже была менее 60 секунд назад, новый HTTP-запрос не создаётся.
2. Если предыдущий запрос ещё выполняется, второй запрос не создаётся.
3. Иначе создаётся одна фоновая задача для нового скользящего окна.
4. `_compute_decision` не ждёт сеть и только читает последний кешированный
   sample.

Таким образом, частые Steam-тики не превращаются в частые HTTP-запросы. Один
активный рынок запускает не более одного refresh-цикла в 60 секунд; только
пагинация внутри полного ответа может потребовать несколько HTTP-страниц.
Отдельный вечный цикл с `sleep(60)` не нужен: первый тик после истечения TTL
запускает обновление, а при отсутствии тиков данные всё равно никому не нужны.

## Поведение live, кеша и рестарта

У карты есть четыре текущих состояния ликвидности:

```text
PENDING      ещё нет ни одного успешного sample
TRADE        последний пригодный sample разрешает BUY с текущим clip_usdc
SKIP         последний пригодный sample ниже MIN_CLIP_USDC
UNAVAILABLE  пригодного sample нет или он старше допустимого возраста
```

У worker отдельно хранятся:

- время последней попытки — оно не даёт долбить API после ошибки на каждом тике;
- время последнего успешного sample — по нему проверяется возраст данных;
- одна выполняющаяся задача — она обеспечивает single-flight для одновременных
  событий.

Успешный sample используется до следующего успешного обновления, но не дольше
`LIQ_FLOW_MAX_AGE_SECONDS = 180`. Если одно обновление упало, предыдущий sample
не исчезает сразу; если источник не отвечает три минуты, новые BUY блокируются.
Следующая попытка разрешена через 60 секунд независимо от результата прошлой.

После каждого успешного обновления заново применяется `choose_clip_usdc`:

- переход `SKIP -> TRADE` разрешает новые BUY;
- переход `TRADE -> SKIP` или `UNAVAILABLE` убирает желаемый BUY, поэтому
  reconciliation отменяет стоящую входную заявку;
- изменение клипа в состоянии `TRADE` меняет желаемое количество, и обычный
  quote reconciliation заменяет заявку;
- SELL и unwind не зависят от кеша ликвидности и остаются разрешены.

При рестарте память кеша не восстанавливается из журнала: старое минутное
решение уже не является текущим. После повторного attach сразу запускается новый
запрос `[now-1200, now)`, а до первого успешного ответа BUY заблокирован.
Исторические записи журнала нужны для аудита, а не для восстановления решения.

Если валидный ответ за полное окно пуст, `rate_per_min = 0` и до следующего
обновления вход пропускается. Короткую жизнь нового рынка не используем как
знаменатель: одна ранняя вспышка не должна искусственно превращать его в
ликвидный рынок.

## Источник потока

Data API поддерживает точные временные границы. Для каждого обновления
`anchor` новый:

```text
GET https://data-api.polymarket.com/trades
    ?market=<conditionId>
    &start=<anchor-1200>
    &end=<anchor>
    &limit=10000
    &takerOnly=true
```

В [актуальном контракте `/trades`](https://docs.polymarket.com/api-reference/core/get-trades-for-a-user-or-markets)
допустим `limit` до `10000`. Ограничение `500`, которое встречается у других
Data API endpoints, к этому запросу не относится.

Расчёт:

```text
taker_notional_usdc = sum(price * size)
rate_per_min        = taker_notional_usdc / 20
```

Требования к загрузке:

- валидировать `timestamp`, `price`, `size`, `conditionId` и конечность чисел;
- не учитывать строки вне `[start, end)`;
- явно передавать `takerOnly=true`;
- использовать документированный максимум `/trades`: `limit=10000`;
- если ответ содержит ровно `10000` строк, дочитать окно через пагинацию, а при
  достижении предела `offset` разделить временной интервал; неполный результат
  нельзя класть в кеш как успешный sample;
- делить на полные 20 минут, а не на `seconds_covered` первой страницы;
- считать `size` количеством shares, поэтому долларовый notional равен
  `price * size`, а не просто `size`;
- сохранять вместе с sample его `anchor`, время успешной загрузки и число строк.

Сетевой код добавить рядом с существующим historical fetch в
`src/live_paper/market_prior.py`. TTL и single-flight принадлежат
`MatchWorker`: сама функция fetch не должна иметь скрытого глобального кеша.
Отдельный модуль или диагностический скрипт для этого изменения не создавать.

## Две настройки и все производные лимиты

`MIN_CLIP_USDC` и `MAX_CLIP_USDC` живут в
`src/shared/constants/strategy.py` и являются единственными числами, которые
надо менять при смене масштаба.

Проверки конфигурации:

```text
MIN_CLIP_USDC > 0
MAX_CLIP_USDC >= MIN_CLIP_USDC
```

Производные значения:

```text
fork base_size_usdc           = 1 * MAX_CLIP_USDC
fork q_max_usdc               = 2 * MAX_CLIP_USDC
risk daily_loss_kill_usdc     = 2 * MAX_CLIP_USDC
risk max_market_notional_usdc = 2 * MAX_CLIP_USDC
risk max_event_group_loss_usdc= 2 * MAX_CLIP_USDC
risk max_total_exposure_usdc  = 4 * MAX_CLIP_USDC
backtest CASH_PER_MATCH       = 1 * MAX_CLIP_USDC
```

При `MAX_CLIP_USDC = $200` это даёт:

```text
base_size_usdc             = $200
q_max_usdc                 = $400
daily_loss_kill_usdc       = $400
max_market_notional_usdc   = $400
max_event_group_loss_usdc  = $400
max_total_exposure_usdc    = $800
CASH_PER_MATCH             = $200
```

Почему внутренний `base_size_usdc` остаётся: замороженный fork требует это поле
и использует его в детекторе sweep. Пользователь его не редактирует;
материализатор всегда подставляет `MAX_CLIP_USDC`. При multiplier `4.0` sweep
должен иметь taker-notional примерно от `4 × MAX_CLIP_USDC` и одновременно
съесть не менее `event_sweep_frac` ближайшей глубины.

Почему risk выводится из максимума, а не из минимума: минимальный клип определяет
допуск тонкого рынка, но максимальный клип определяет худший размер одного fill.

Шаблон `config/dota-map.toml` не содержит редактируемых копий этих долларовых
чисел. `session_config.py` при создании временного fork-конфига подставляет все
производные значения. Поэтому `q_max` и daily kill всегда соответствуют
выбранному `MAX_CLIP_USDC`.

Не масштабировать от размера:

- `merge_min_size` — это shares, а не USDC;
- `event_sweep_mult`, `event_sweep_frac`, `q_soft_frac`, `resize_frac` — доли и
  множители;
- таймеры, число тиков, heartbeat и error rate.

Эти настройки читаются из шаблона без масштабирования.

## Risk должен реально применяться в Dota-quoter

Fork вычисляет `risk_size_scale` и режим `REDUCE_ONLY`. Кастомный Dota-quoter
обязан применять оба результата; иначе путь BUY обходит рассчитанные лимиты.

Целевое правило размера после risk-проверки:

```text
final_entry_usdc = current_clip_usdc * clamp(risk_size_scale, 0, 1)
```

- `risk_size_scale` может только уменьшить текущий клип, но никогда не
  увеличить его;
- если рынок находится в `REDUCE_ONLY` и позиции нет, новый BUY не ставится;
- если позиция уже есть, SELL остаётся разрешён;
- если после risk scale размер ниже CLOB minimum, ордер не ставится;
- hard risk caps считают уже исполненную позицию, поэтому максимальный клип и
  применение soft scale остаются обязательной защитой от перескока через cap.

Flow layer меняет исходный клип не чаще раза в минуту. Risk layer может на
каждом тике дополнительно уменьшить фактическую заявку при изменении общей
экспозиции.

## Контрольный пример и ограничения анализа

Матч `8962592819` не является доказательством мёртвого рынка. В фиксированном
окне `[horn-1260, horn-60)` Data API с `takerOnly=true` вернул notional около
`$4,698`, то есть примерно `$235/мин`. Правило расчёта даёт клип около `$11.75`
и разрешает торговлю. Число около `$453/мин` получается при суммировании
`size` как долларов; это неверно, потому что `size` измеряется в shares.

Его фактическая заявка была 454.55 shares по `$0.22`, то есть `$100`, а fill —
87.36 shares, то есть около `$19.22`. Fill составил около 19.2% от связанной с
ним заявки. Сопоставление с другой заявкой на 769 shares дало бы неверные 11%.

Корреляция flow с fill fraction не является доказательством полезности правила,
если расчёт имеет следующие свойства:

- в выборку попали только ордера с ненулевым fill;
- flow измерялся в момент fill, а не постановки ордера;
- fill связывался с максимальной заявкой карты, а не со своим `order_id`;
- несколько fills одной карты считались независимыми наблюдениями.

Значение `LIQ_FLOW_MULT_PER_MIN` — гипотеза управления размером. Её пользу
проверяет backtest с нулевыми fills и точной связью fill с исходным ордером.

### `src/shared/constants/strategy.py`

Добавить две пользовательские ручки и фиксированные правила:

```python
MIN_CLIP_USDC = 10.0
MAX_CLIP_USDC = 200.0
LIQ_FLOW_MULT_PER_MIN = 0.05
LIQ_FLOW_WINDOW_SECONDS = 1200
LIQ_FLOW_REFRESH_SECONDS = 60.0
LIQ_FLOW_MAX_AGE_SECONDS = 180.0
LIQ_FLOW_PAGE_LIMIT = 10_000
```

Удалить независимый `BASE_SIZE_USDC`. В этом же модуле определить
производные dollar limits, чтобы live и backtest импортировали одну реализацию.

Чистая функция `choose_clip_usdc(rate_per_min)` возвращает `TRADE` с размером
или `SKIP`. Неизвестность источника в эту функцию не передаётся.

### `config/dota-map.toml` и `src/live_paper/session_config.py`

- удалить ручное дублирование `base_size_usdc`, `q_max_usdc` и четырёх
  долларовых risk limits из шаблона;
- сохранить операционные risk-параметры без изменения;
- обновить строгую входную схему шаблона;
- перед записью временных `config.toml` и `strategy.toml` добавить вычисленные
  fork-поля и risk limits;
- журналировать итоговые вычисленные значения при старте процесса.

### `src/live_paper/market_prior.py`

Добавить строгий historical fetch taker flow для переданного `anchor`. Он
запрашивает `[anchor-1200, anchor)`, полностью дочитывает окно и возвращает
типизированный sample с anchor, notional, rate и числом trades либо
типизированную ошибку. Отрицательные числа и NaN как sentinel не использовать.

### `src/live_paper/match_worker.py`

- хранить последний успешный sample, monotonic-время последней попытки и
  последнего успеха, а также не более одной задачи загрузки;
- при attach сразу вызвать `_maybe_refresh_flow`, затем вызывать его на каждом
  Steam-событии;
- не создавать запрос, если последняя попытка была менее 60 секунд назад или
  задача уже выполняется;
- запрос выполнять в фоне через существующий async/http путь, не делать I/O в
  синхронной `_compute_decision`;
- на успехе атомарно заменить sample и опубликовать новый клип через
  `StrategyState`;
- на ошибке сохранить прежний sample, но не использовать его после 180 секунд;
- при остановке worker отменить выполняющийся запрос;
- после рестарта не восстанавливать старый клип, а сразу получить текущее окно.

### `session_types.py` и `session_quoting.py`

- `StrategyState` получает текущий `entry_size_usdc` и возраст flow sample;
- `EntryBlock` получает раздельные причины `LIQUIDITY_PENDING`,
  `LIQUIDITY_UNAVAILABLE`, `THIN_MARKET` и `RISK_REDUCE_ONLY`;
- `_entry_quotes` использует текущий размер из state и применяет
  `risk_size_scale`;
- при новом `SKIP`, `UNAVAILABLE` или новом размере обычный reconciliation
  отменяет либо заменяет уже стоящий BUY;
- flat market в `REDUCE_ONLY` не создаёт BUY;
- exit-path не менять.

### `session_journal.py`

После каждого успешного обновления, но не чаще раза в минуту, писать
`liquidity_sample`:

```text
policy_version
condition_id
anchor_ts
window_start_ts
window_end_ts
taker_notional_usdc
flow_rate_per_min
trade_count
min_clip_usdc
max_clip_usdc
raw_clip_usdc
clip_usdc
decision = trade | skip
sampled_at_utc
```

Записи с разными `anchor_ts` являются нормальной историей изменения потока, а
не конфликтующими решениями. В `signal` писать использованный `anchor_ts` и
возраст sample, чтобы было видно, на основании какого обновления создана заявка.

В quote-запись добавить `order_id`, цену, shares и submitted notional, чтобы
partial fills можно было связывать с настоящей заявкой, а не с максимумом карты.

## То же минутное правило в offline backtest

Речь идёт о существующем offline backtest в `src/backtest`, который проигрывает
исторические Telonex L2 books с моделью очереди и частичными fills. Live paper
исполняет заявку целиком по лимиту и не может честно показать эффект размера.

В backtest нельзя заранее вычислить один flow или один клип на всю карту. На
каждом историческом state-событии стратегия обращается к минутному кешу точно
так же, как live. Отличаются только источник данных и часы: вместо HTTP
используется уже загруженная архивная лента trades, а время берётся из
проигрываемого события.

Один раз читается только файл с историческими trades. Это оптимизация I/O, а не
одноразовый расчёт размера. Во время replay правило работает так:

1. На первом state-событии посчитать notional для завершённого окна
   `[event_ts-1200, event_ts)`.
2. На каждом следующем state-событии проверить возраст кеша. Если с прошлого
   расчёта прошло меньше `LIQ_FLOW_REFRESH_SECONDS`, вернуть прежний sample без
   пересчёта.
3. После истечения 60 секунд сдвинуть окно, заново применить
   `choose_clip_usdc` и обновить текущий `entry_size_usdc`.
4. Если архив trades карты отсутствует или невалиден, считать flow
   `UNAVAILABLE`, а не нулевым.
5. Переходы `SKIP -> TRADE`, `TRADE -> SKIP` и изменение клипа должны так же
   разрешать, отменять или заменять BUY через обычный quote reconciliation.

Константы окна, refresh, multiplier, min/max и функция `choose_clip_usdc` общие
для live и backtest. Отдельной backtest-формулы и отдельного фиксированного
размера нет. Пересчитывать сумму с нуля при refresh не нужно: указатель по
отсортированной ленте и rolling sum дают тот же результат без повторного чтения
файла.

При чтении collector parquet учитывать trade только один раз: не суммировать
зеркальные записи обеих token partitions.

Сравнить на одинаковых матчах и с одинаковым стартовым капиталом
`MAX_CLIP_USDC`:

- baseline: фиксированный вход `$100`;
- candidate: минутный rolling flow с `MIN_CLIP_USDC = $10` и
  `MAX_CLIP_USDC = $200`.

Смотреть общий и поматчевый PnL, fills вместе с нулевыми, максимальную
экспозицию, остатки после выхода, blocked profitable fills и markout. Результаты
группировать по карте, а не считать каждый fill независимым матчем.

Отдельный `scripts/replay_flow_filter.py` не создавать: минутный расчёт добавить
в существующий backtest runner и его отчёт.

## Проверка

1. Формула:
   - `raw_clip < MIN` даёт `SKIP`;
   - равенство с `MIN` разрешает вход;
   - середина даёт `LIQ_FLOW_MULT_PER_MIN × flow`;
   - выше `MAX` зажимается в `MAX`.
2. Производные настройки при `$10 / $200` равны
   `$200, $400, $400, $400, $400, $800` согласно таблице выше.
3. Невалидные `MIN <= 0` и `MAX < MIN` останавливают старт до attach.
4. Data API: пустое окно, нормальный ответ, пагинация, HTTP failure, битый JSON,
   невалидные числа и строки вне окна.
5. Кеш: attach запускает первый запрос; много тиков за 60 секунд не создают
   дополнительных запросов; одновременные вызовы используют одну задачу.
6. Refresh: первый тик после TTL создаёт новый запрос и новое rolling window;
   `SKIP -> TRADE`, `TRADE -> SKIP` и изменение размера меняют желаемый BUY.
7. Ошибка: не вызывает запрос на каждом тике, предыдущий sample живёт не более
   180 секунд, после чего BUY блокируется; следующий минутный refresh может
   восстановить торговлю.
8. Restart: старый sample не восстанавливается как текущий, сразу запрашивается
   окно относительно нового `now`, а до ответа BUY отсутствует.
9. Risk: клип `$100` при scale `0.4` создаёт BUY примерно на `$40`; flat
   `REDUCE_ONLY` не создаёт BUY; SELL позиции остаётся.
10. Backtest: много simulated ticks внутри 60 секунд используют один sample;
    после 60 секунд окно и клип обновляются; переходы между `TRADE` и `SKIP`
    меняют outstanding BUY так же, как в live.
11. Backtest baseline `$100` против минутного flow sizing на одной выборке.
12. `make lint-all` и `uv run pytest`.
13. После успешных тестов выложить изменение и один раз выполнить
    `docker compose restart live-paper`.

Отдельных режимов `shadow/enforce` и второго restart нет.

## Вне этой задачи

- Не менять модель, цены входа, остальные model gates и выход.
- Не менять `poly-maker`: fork заморожен.
- Не исправлять здесь retry для market prior; это отдельный дефект и отдельный
  коммит.
- Не пытаться предсказывать fill fraction только по flow.
- Не масштабировать вручную параметры, которые измеряются не в USDC.

## Критерии готовности

- Пользователь меняет только `MIN_CLIP_USDC` и `MAX_CLIP_USDC`.
- Все dollar risk limits, внутренние `base_size/q_max` и backtest cash выводятся
  автоматически.
- Daily loss kill также автоматически равен `2 × MAX_CLIP_USDC`.
- После attach поток обновляется не чаще одного раза в 60 секунд, независимо от
  количества Steam-тиков.
- Размер и решение могут измениться только после успешного минутного refresh.
- Offline backtest использует тот же rolling window и тот же refresh раз в 60
  simulated seconds; один раз читается только исходный trade-файл.
- Restart немедленно создаёт новый sample текущего rolling window.
- `8962592819` при dollar-notional около `$235/мин` получает клип около `$11.75`
  и не блокируется минимумом `$10`.
- Dota BUY реально подчиняется `risk_size_scale` и `REDUCE_ONLY`.
- SELL и unwind продолжают работать независимо от liquidity gate.
