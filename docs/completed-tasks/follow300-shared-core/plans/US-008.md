## Outcome and scope

Both adapters use one accepted Follow300 policy with:

1. Late fills attributed to the order's original episode and actual token,
   including fills received after cancel ack and after the opposite-token
   episode starts. Unresolved ownership prevents new BUY until reconciled.
2. One SELL decision table: MATCHED hold, 1-second minimum life, 10-second
   settle after a BUY fill, and immediate emergency cancellation. BUY remains
   available within the existing permissions and reserves.
3. Book/signal wakeups coalesced over 100 ms and a 2-second fallback in both
   adapters, using the values from `config/trading.toml` `[engine]`.

Ship these as three named, reviewable changes with compact before/after evidence.
Suggested successive versions: `follow300-v2` (ownership), `follow300-v3`
(SELL), `follow300-v4` (cadence). The final application has one active policy;
these versions identify commits and evidence, not runtime strategy choices.
Recheck the existing version before implementation to avoid reusing a version.

## 2. Named change A: preserve late-fill ownership and token inventory

### Core representation and transitions

Extend the frozen types with retained order ownership and an explicit two-token
inventory representation. Retained ownership includes order/episode/token/side,
last assigned rung, submitted and cumulative filled quantity, and terminal state.
Keep active orders separate from retained records: a terminal binding is neither
a resting reserve nor an occupied rung. Retain records for the map session; an
arbitrary short TTL would recreate the delayed-fill bug.

Keep per-episode fill/rung attribution after the active episode ends. Updating an
archived episode must not change the new episode's `has_buy_fill`, rung `done`,
`live_id`, token latch, or winding-down state. Preserve move-at-fill semantics:
use the last actual rung assignment, not always the original submit rung.

Use per-token quantity, cost basis, and last-BUY time as the inventory source of
truth. Derive any convenience selected-position view from those values. Do not
maintain a writable scalar position in parallel or create a second wallet cash
ledger. BUY credits its actual token; SELL debits its actual token. Check total
holdings, including both dust balances, before declaring the session flat.

For the exceptional two-token state, keep at most one outstanding SELL across
the market. Keep its token while it is outstanding; when a fresh SELL is needed,
use the existing live selection order (larger sellable holding, YES on ties),
then drain the other token when eligible. Retain both balances throughout. A
known old-episode fill does not by itself turn the entire map permanently
sell-only. The BUY latch remains the active episode's token. SELL attribution
uses retained order ownership; never infer a fill's owner from aggregate size.

Implement two distinct fill cases:

- **Known active or terminal order:** apply the economic fill once and attribute
  it to its recorded episode/rung. A post-cancel partial fill updates the retained
  record without resurrecting a resting order or reserving its canceled remainder.
- **Unknown or contradictory ownership:** preserve the event and immediately
  block/cancel BUY with a specific `ownership_unresolved` reason. Adapters supply
  actual token/side from the venue/ledger fill, extending the normalized Fill
  input as needed. Distinguish inventory credit from pending episode attribution:
  resolving a binding later must apply the missing attribution exactly once and
  must not credit the position twice. Do not add to a dedup set and discard the
  only replayable event.

Resolve ownership through a typed input carrying proven order metadata from the
existing durable bindings/command/outbox path. Clear the temporary block only
after all pending ownership is resolved and inventory agrees with the adapter.
Revalidate permissions and budget before the next BUY. If proof requires the
US-006 recovery path, retain its permanent sell-only rule; an ownership-resolution
event must never clear an existing restart/FAILED recovery restriction.

## 3. Named change B: make the SELL table common

Use the existing common quoting implementation. Make 1-second minimum life and
unconfirmed hold properties of the accepted policy, not live-only choices.
Backtest normal fills are immediately confirmed; delayed settlement remains a
normalized adapter/fixture input, not an invented historical fill model.

Apply the following precedence at a permitted quote evaluation:

| Situation | Existing SELL | New SELL | BUY |
| --- | --- | --- | --- |
| HALT, game end, pause, or recovery drain | Cancel immediately, even inside min-life/MATCHED hold | None | Block/cancel as required |
| `allow_sell=False` for the exit token | Cancel through the established permission path | None | Independent permissions/budget |
| MATCHED unconfirmed on either token | Keep eligible existing SELL at its remaining size and price | None | Continue within permissions/reserves |
| No unconfirmed hold; successful SELL place age < 1 s | Keep eligible existing SELL, including after a new BUY fill | None | Continue within permissions/reserves |
| Last BUY for the exit token < 10 s ago; neither hold applies | Cancel working SELL | None | Continue within permissions/reserves |
| Settle expired, no hold | Keep if price/remaining size matches; otherwise cancel and wait for ack | Place only when no unresolved SELL occupies the slot | Continue within permissions/reserves |

Book/fair validity and existing emergency gates still apply. A canceling SELL or
an unknown cancellation outcome is not a hold target. It occupies the slot until
resolved, preventing a duplicate SELL. If no order exists, neither min-life nor
MATCHED hold creates a synthetic order.

Start minimum life at successful place acknowledgement, not decision construction.
Carry that timestamp through the queued acceptance event, retained order state,
Nautilus adapter and persistence. A duplicate ack cannot restart the timer. A
submit timeout remains unknown; do not invent a successful-place timestamp.
Keep BUY settle based on normalized receipt/application time in this step, as the
current core does; an old exchange timestamp must not move core time backwards.
CONFIRMED for an already credited MATCHED neither credits again nor restarts settle.

Unify the held, normal, and recovery SELL decisions enough that min-life and
settle cannot disagree between early-return branches. In particular, no BUY
targets plus a settling SELL must not accidentally keep SELL indefinitely.
Use one small SELL decision function rather than duplicating the table in live,
backtest, and recovery code. Emergency cancellation remains outside its holds.

Extend the contract tape with a normalized settlement-status event. Its live
producer must use `WalletStateStore.apply_matched_fill`, `apply_confirmed_fill`,
and `apply_failed_fill`, or their existing production normalization seam. Drive
the backtest adapter with the resulting same inventory/permission sequence.
Test MATCHED→CONFIRMED and MATCHED→FAILED, multiple outstanding MATCHED keys,
and CONFIRMED without prior MATCHED. FAILED verifies ledger rollback plus
US-006 recovery; it is not a second positive Fill or a fake confirmation.

Boundary assertions: 999,999,999 ns versus 1,000,000,000 ns after successful
place; 9,999,999,999 ns versus 10,000,000,000 ns after the latest BUY; a second BUY
resetting settle; an unconfirmed hold beyond 10 seconds; confirmation before
and after settle expiry; slow submit; cancel timeout; partial SELL remaining
size; emergency cancel during both holds; and a full BUY rung continuing while
SELL is held. Refresh book/signal freshness in long scenarios so these checks
exercise the SELL rule rather than `stale_book`.

## 4. Named change C: use the same real schedule

### Configuration and deterministic scheduling

Pass typed cadence settings to the policy from the adapters. Read `[engine]`
`debounce_ms=100` and `quoter_tick_s=2.0` once through a shared adapter-config
reader; do not make backtest import trader or put filesystem/TOML access in
`src/strategy`. Reuse `session_config.py`'s validation by extracting its narrow
engine-settings portion into `shared` if needed. Keep profile sizes independent.
Record effective values in the backtest manifest and checkpoint policy identity.

Put scheduling state and deadline selection in a small pure
`strategy/scheduling.py` helper used by the core, rather than expanding the
existing large adapter files with another copy of the timing rules.

- First book or signal update opens a fixed 100-ms window. Later updates in
  that window replace inputs without pushing its deadline. The quote uses the
  latest complete pair and latest signal available at that deadline.
- With no pending dirty window, reevaluate after 2 seconds without a quote.
  A dirty window supersedes that idle fallback; a burst beginning just before
  its expiry is evaluated at the first dirty time + 100 ms, matching the live
  coalescing model. Continuous books cannot starve evaluation.
- Apply order/fill/status events immediately in arrival order. Ordinary
  place/fill-driven quote requests use the same coalescing window. CancelAck
  and verified recovery retain their immediate reevaluation behavior, and
  their commands must reach execution. Emergency permission/clock changes
  bypass coalescing and cancel immediately when received.
- Schedule the next relevant 1-second minimum-life or 10-second settle boundary
  when that boundary can change SELL action; it may preempt the ordinary window.
  This precise expiry wake is part of the labeled cadence change and must be
  shown in the before/after report. Do not continuously rearm an expired or
  irrelevant deadline while MATCHED still prevents a SELL change.
- `next_wake_ns` is the actual earliest outstanding deadline, not
  `last_input_ns + 2s`. Repeated data-only inputs cannot postpone it. Stale timer
  callbacks are ignored by a generation/deadline check; equal timestamps keep
  stable receipt order. Already-applied events are never sorted by trade time.

### Backtest scheduler

Replace the hard-coded `REPRICE` loop with a single reschedulable wake driven by
core output. `on_order_book_deltas` must emit the updated snapshot; explicit
alerts at existing feed/signal receipt timestamps must emit SignalUpdate or a
signal invalidation. Keep feed cadence generation and `SignalTiming(seed=...)`
unchanged: quote cadence is a different clock. Do not query a future preloaded
signal simply because its timestamp is present in the config.

Both token snapshots must be applied in deterministic input order, preserving
the current incomplete-book handling. Cutoff continues to represent game second
540 using the existing pause-aware `buy_cutoff_ns`; no data-delay or order-latency
offset is added. Game-end/cutoff callbacks and order acknowledgements retain
their cancellation guarantees. Check callbacks at the same nanosecond against
the existing cancel-send workaround; do not alter matching latency to make a
scheduler assertion pass.

Replace `_live_order_ticks` with accumulated elapsed nanoseconds during the union
of intervals with at least one outstanding order. Update it on order-set
transitions and at game end, so uptime remains seconds under any quote cadence.

### Live scheduler and queue execution

Install a per-engine esports scheduler from `trader/engine_seams.py` or a focused
new `trader/core_scheduling.py`, wired in `host_resources.py`. Use the existing
market lock, gateway, risk calculation and core-plan executor. Patch the narrow
quoter/dirty notification seams from esports-trader; restore them on teardown.
Do not add another 100-ms sleep on top of the fork's debounce.

Book and signal arrivals must reach the core/scheduler before quote time.
`sync_inputs` refreshes budget/permissions at execution, but must not manufacture
new dirty book events merely by rereading an unchanged snapshot. Recompute the
budget after queued fills are applied and before admitting placements.

Preserve commands produced while draining events. `LiveCore.apply` currently
drops `next_wake_ns`, and several worker callbacks discard `drain_apply()`'s
return; refactor those seams so each plan is staged/executed exactly once.
Persist intents before network await as in US-006, and revalidate the staged
places after any intervening emergency/cancel/fill. A callback may not create a
pending order in state whose Place command never reaches the gateway.

Test attach/detach, shutdown cancellation, event arrival during an awaited
gateway call, timer rescheduling, and emergency cancellation with an incomplete
book. An early return inside the fork's quote calculation must not bypass a
core HALT cancellation or prevent the next fallback from being armed.
