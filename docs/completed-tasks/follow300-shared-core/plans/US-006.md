# US-006: Persist core state and drain mid-episode recovery

Project: `../esports-trader`, branch `ladder-experiment`.
Inspected HEAD: `1f13a64724dc9a74e023f598c753e0586bb8e9f7` (US-005 review fixes).
Selected from `feature.json`: priority 6, the first pending step. US-001–US-005
are marked passed; the older “leave passes false” progress entries are historical.
This document plans US-006 only. It does not implement it or change its pass flag.
No Figma links or UI designs are supplied.

## Outcome and scope

A restarted map restores durable order ownership, cancels its old orders, waits
for their terminal outcomes and trade settlement, verifies inventory, and then
sells that inventory. That map remains sell-only after becoming flat and across
further worker/process restarts. A genuinely new map in the same wallet process
can still open the ordinary ladder.

The wallet ledger remains the source of cash and position accounting. Core
checkpoints are decision/ownership state, not another wallet. The existing
`session.jsonl` schema stays v6; neither ladder restoration from journals nor
the US-009 decision trace belongs here.

Keep current clips, caps, cadence, and ordinary SELL policy unchanged. US-007
owns configuration/shared-budget expansion; US-008 owns its three labeled
normal-trading changes. Recovery-specific cancellation and verification gates
are the intentional behavior change in this step. Do not recapture extraction
goldens, run the 12-seed baseline, operate a daemon/VPS, merge, or edit poly-maker.

| `trader/match_worker.py`, `_try_attach`, `_restore_open_round` | A new core is exposed before restore; a matching journal restores only the settle timestamp. Flat/remainder-only restarts can keep BUY enabled. |

The frozen fork was inspected read-only. `ExecutionGateway.place` signs and posts
inside one `_io` closure; the Engine may skip a planned place after cancel failure
or load shedding. Its startup reconciliation also cancels before workers exist.
These are concrete integration cases, not reasons to change the fork.

## Approach and ownership

Use an explicit, typed checkpoint plus durable commands in the **existing wallet
SQLite database**, and a small recovery coordinator in `trader/`. Keep all core
transitions on the current serialized queue. The coordinator gathers venue and
ledger evidence; only events passed to `strategy.engine.step` change core state.

This is preferable to replaying `session.jsonl`, which lacks ownership and pending
commands. A full event-sourced wallet/strategy rewrite would duplicate the ledger
and overlap US-009. Checkpointing only at shutdown would leave the crash windows
in the acceptance criteria open.

Suggested module boundaries:

| File | Responsibility |
| --- | --- |
| New `src/trader/core_persistence.py` | Frozen checkpoint/binding/command types, strict versioned encoding, SQL operations executed on the wallet connection. |
| New `src/trader/core_execution.py` | Persist the actual place/cancel attempt before dispatch; persist results before queue delivery; reconcile commands never sent. |
| New `src/trader/core_recovery.py` | Session classification, order/settlement proof, position verification, and recovery progress. |
| `wallet_store.py` | Own the connection and transaction boundaries; expose narrowly typed ledger/outbox/recovery queries. |
| `session_core.py` | Export/restore structural state, consume durable events, aggregate plans and retain the recovery lock. |
| `wallet_host.py`, `match_worker.py`, `host_resources.py`, `engine_seams.py` | Wire the above into boot, attach, gateway seams and teardown. Keep these changes small. |
| `strategy/types.py`, `lifecycle.py`, `engine.py`, `quoting.py` | Pure recovery start/verification transitions and recovery-only SELL gating. |
| `backtest/strategy.py` | Public adapter recovery methods translating explicit inputs to the shared events and executing their plans. |

Avoid adding another large block of persistence/recovery methods to MatchWorker
or engine_seams. No `__init__.py`, untyped internal dictionaries, or anonymous
multi-field tuples; follow the project’s required-argument and action-verb rules.

## 1. Durable identity, state and transactions

Add idempotent tables/migrations alongside the existing ledger schema:

| Record | Required contents |
| --- | --- |
| `core_sessions` | Stable session ID; condition ID, game, YES/NO tokens and orientation; schema/policy identity; revision; sticky recovery flag; structural checkpoint; last consumed fill-outbox sequence. |
| `core_order_bindings` | Session/core order ID, venue ID when known, episode, token, side, submitted quantity, and last rung assignment. Preserve terminal bindings for delayed fills. |
| `core_commands` | Durable command ID, session/revision/batch identity, place or cancel, target core ID, exact final quote, known/signed venue ID, dispatch state, durable outcome and whether the checkpoint consumed it. |

Use the condition and immutable token binding to find an existing session. Do not
use the current Steam match ID, archive directory alias, or transient worker as
the identity: this code already supports handoffs. The wallet identity pin still
guards the database. `c0` is unique only inside one core session; qualify every
persisted key. New core sequence numbers must not collide with restored bindings.

The checkpoint carries episode counters/latch ownership, actual saved rungs,
active orders, seen fill IDs, winding-down/sell-only/recovery state, and timing
information needed for drain. Do not serialize books, model signals, available
cash or transient permissions as trusted startup inputs. Store last BUY/place
times in restart-safe wall-time form; rebase durations to the new monotonic clock.
Do not use pickle or a generic recursive dataclass deserializer.

Checkpoint and binding projections must update in one transaction, including
queue-preserving rung moves. Preserve a binding after an order leaves the active
snapshot so a late venue fill retains its actual episode and last assignment.
Validate duplicate IDs, token/session mismatches, schema versions and nonfinite
numbers at the adapter boundary. Missing legacy metadata selects recovery;
corrupt/newer metadata must not silently create a fresh BUY session.

Use the wallet’s single connection on its owning event-loop thread. SQL helpers
must not open/commit nested transactions under the fill transaction. Retain WAL
and explicitly verify a durability setting appropriate to acknowledged commits
(`synchronous=FULL`); never disable sync for quote throughput.

### Independent core consumption of fills

Keep `fill_outbox.acked` dedicated to existing journal effects. Add a per-session
core cursor in the checkpoint and read the existing outbox **including acked
rows**, ordered by `seq` and filtered through the session’s token binding. The
current outbox rows are retained, so a second copy of fill accounting is unnecessary.

For each consumed event, commit the new checkpoint, binding changes and cursor
together, then publish the new in-memory state. On failure, restore the last
committed state and stop dispatching that session’s places. A subsequent drain
replays the same row. Never acknowledge the core merely because an event entered
the in-memory deque.

MATCHED credits once; CONFIRMED after that changes settlement state without
crediting again. Standalone CONFIRMED credits once. FAILED invokes recovery of
the ledger’s rebuilt position. Retain dedup IDs in the checkpoint. Do not use a
fill’s timestamp as the consumption cursor; late timestamps are valid. Do not
advance past an unresolved binding unless that unresolved fill is itself durably
retained for reconciliation.

For a fill whose known terminal order is no longer in the active snapshot, retain
its processed key and saved ownership and invalidate recovery verification. Use
the verified ledger position to reconcile the recovery inventory; do not silently
drop it in `LiveCore.note_fill` or recreate a live rung/reservation. The broader
normal-trading old-episode fill change remains US-008.

Process newly committed fills through this same consumer during normal operation;
replace the current best-effort `_on_fill_credited` delivery with a wake/drain
notification. If no worker exists yet, the row stays available. The journal may
still complete its own work independently.

On restart, load durable order outcomes/bindings before replaying the outstanding
fill rows, enter recovery before replay can produce places, and reconcile the
final ledger inventory after replay. Do not initialize the core from the ledger’s
latest aggregate size and then add the outstanding fills to that size again.
This reconstructs ownership for drain; it does not replay old model decisions.

## 2. Make the network boundary durable

Persist the finalized core batch and its structural checkpoint before the Engine
can await cancellation/placement. Keep a distinct `prepared` versus
`dispatch_started` state: a generated quote is not evidence that a POST ran.
Persist each outcome before enqueuing its corresponding core event. Commit the
checkpoint and outcome-consumed marker together when that queue event is applied.

For place, cover the response-lost window by recording the venue order hash before
POST, rather than reconstructing an order from price and quantity after restart:

1. Prepare/sign the exact finalized quotes using the existing SDK, tick/neg-risk
   options, GTC and post-only settings. Signing may await SDK metadata; no order
   submission has occurred at this stage.
2. Derive each hash from that **same signed order** and persist its binding plus
   dispatch intent on the event-loop thread before scheduling POST.
3. Post those same signed objects. Commit per-command results, then enqueue
   acceptance/timeout/rejection events. Do not sign a new order on timeout.

The installed `py_clob_client_v2` exposes
`ExchangeOrderBuilderV2.build_order_typed_data` and `build_order_hash`; its builder
selects the normal/neg-risk contract from chain config. Reuse these implementations
with the actual signed V2 order, not hand-written hashing or new salt generation.
Add a fixed SDK fixture that checks the precomputed ID against the expected
exchange order ID and verifies the response binding. An ID disagreement leaves
the command unresolved. Do not claim that a missing response is a rejection.

After preparation awaits, recheck session generation, shutdown/HALT and whether
the batch is still executable before marking dispatch started. Retire a canceled
prepared command as known-not-sent. Bind response entries by their persisted
order identity; retain unknown siblings when a batch has partial/malformed results.

This seam adds coupling to the installed SDK's signing API. Keep that coupling
inside `core_execution.py` and test normal/neg-risk contract selection. It buys a
stable lookup key for lost responses; it does not make SQLite and the exchange
one transaction or prove settlement from an HTTP acknowledgement.

Implement this as an esports-owned gateway seam installed inside the existing
shutdown/rate/SELL-guard/journal wrappers. Preserve parser error-rate and balance
reject hooks. Never write SQLite from the SDK worker thread. PaperGateway remains
a fixture transport and does not need CLOB signing or a running paper daemon.

Cancel intents bind to durable venue IDs and persist before DELETE. Route outcomes
using these bindings even if the fork already removed an order from `state.orders`
or no MatchWorker is attached. The existing boolean cancel API may conservatively
leave a partially successful batch unresolved; follow-up per-ID proof resolves it.
Cancel retries are safe; place retries after uncertain dispatch are forbidden.

Wrap the existing `_recompute_locked` call from esports-trader to close the case
where the fork consumes a plan but never invokes place (cancel failure, load
shedding, early exit). At completion, release only commands still proven
`prepared`/not dispatched through an explicit known-not-sent core outcome. A
dispatched command retains its reservation until reconciled. Do not leave phantom
pending rungs, resend a stale `_last_batch`, or introduce another quote diff.

Pre-send persistence failure prevents the POST. Failure after POST leaves a
durable unknown command from the pre-send commit and puts the session into recovery.
Track completion of shielded/in-flight work before retiring an old worker; a
timeout or task cancellation must not masquerade as proof that POST never ran.

## 3. Explicit recovery barrier in the shared core

Keep `sell_only` as the permanent session lock and add `recovery_pending` as the
temporary proof barrier. Extend the existing Recovery contract and add a typed
`RecoveryVerified` event carrying the selected verified Position, rebased last-BUY
time and a recovery generation. Both adapters drive these through `step()`.

| Transition | Required behavior |
| --- | --- |
| Recovery starts | Set sell-only and pending before any place. Cancel restored BUY. Also cancel pre-restart SELL so verification has no moving old exit order. Retain ownership and BUY reserves. |
| Cancel timeout / unknown submit | Remain pending. No new BUY or SELL; retry only cancellation/status reads. |
| Fill during drain | Ledger credits once; the serialized core path records known ownership. Invalidate any position-verification result collected before this fill. |
| Orders terminal, settlement resolved, inventory verified | Accept the current generation’s RecoveryVerified event, synchronize position/cost basis and settle time, and clear pending. Sell-only remains true. |
| Flat or dust-only | Keep sell-only. Never rebuild BUY levels or infer completed rungs from inventory. |
| New map | A different durable session starts with the normal policy. |

Recovery itself must not clear the 10-second settle timer. Only verified timing
can replace it. An early/duplicate/stale RecoveryVerified must not bypass pending
orders or a newer recovery generation. A normal PermissionsUpdate cannot clear
either recovery flag. HALT and emergency cancellation still take precedence.

Gate recovery before ordinary quoting can mint orders. Return cancellation plans
even when books/signals are absent. Once verified, use a recovery-only SELL path
in `strategy/quoting.py`: fresh usable books and ordinary SELL permissions/minimums
are required; use a valid current fair when available, otherwise join the ask.
Do not fabricate a model signal, cross the spread, or route through a second
adapter quoting implementation. This makes exit-only recovery work without
waiting for a model that may no longer publish past cutoff. Ordinary trading
retains its current signal, min-life, settlement and cadence behavior.

Update `LiveCore.finish_cycle` to collect actionable plans from **all** events it
applies. It currently discards plans from `sync_inputs`, including mismatch
Recovery. Retain the cancellation sweep, but do not rely on it as a substitute
for executing Recovery/RecoveryVerified plans. Recheck accumulated places against
the final state so a later Recovery in the same drain cannot release an earlier BUY.

## 4. Startup and proof sequence

1. **Classify before attach can quote.** Load durable sessions/commands at host
   startup, before `engine.start()` can cancel old orders. Capture legacy journal
   freshness before writing a new `session_start`. Existing session metadata,
   an owned previous journal, old orders or ledger inventory selects recovery,
   including flat or dust-only sessions. A failed/retried worker for the same map
   is not fresh. Preserve existing provenance refusals for foreign bindings.
2. **Make the lock durable.** Persist the recovery flag/generation before exposing
   the core to the quoter, registering callbacks, or replaying outbox effects.
   Load real saved links; legacy orders lacking links remain explicit orphans,
   with no invented episode/rung assignment.
3. **Drain orders.** Reuse strict cancellation proof for known IDs and token-scoped
   cancellation for legacy/unmapped orders. Reconcile signed hashes through
   order status/trade history, including orders filled before the response.
   Include pre-restart SELL in the fence. A cancel-all call or absence from a
   single open-orders read alone is not terminal/settlement proof.
4. **Resolve settlement.** Query durable MATCHED rows, not only `inflight()` (which
   the fork can expire) or journal acknowledgements. Fetch trade outcomes over
   the persisted unresolved interval, with pagination and an overlap for dedup;
   do not cap recovery at the periodic one-hour lookback. Handle explicit
   CONFIRMED and FAILED via existing ledger methods. Missing/malformed statuses,
   MINED/RETRYING or failed reads do not prove terminal settlement for recovery.
5. **Verify both token balances.** Drain newly committed ledger effects, then
   obtain successful complete token-balance reads using the gateway’s strict
   batch API (`token_balances` returns None on failure). Recheck the ledger and
   command revision after the await. If either changed, repeat verification.
   Compare in supported share units; do not use the general divergence tolerance
   of one share/2% to authorize an oversized recovery SELL. Reconcile through the
   existing wallet position APIs without changing ledger cash or inventing fills.
6. **Open the verified exit.** Enqueue RecoveryVerified with current evidence and
   drain through the normal adapter plan executor. Subsequent fills/FAILED or
   unexplained position changes re-enter verification before a replacement SELL.

Implement the stricter recovery read/status path in `core_recovery.py` using
existing parsers/ledger APIs where their semantics fit. The periodic backfill
wrapper swallows failures and defaults absent statuses to CONFIRMED; do not reuse
that behavior as proof or silently change its non-recovery semantics in this step.

Legacy journals do not prove which BUY rung was filled. Cancel/fence by the
session’s two tokens, reconcile trades and balances, then use the same verified
exit path. An unidentifiable or unproven order remains a visible recovery blocker;
elapsed time never authorizes a replacement place.

Restore reservations before admitting the first new-map BUY, including durable
pending/unknown orders for sessions discovery has not reattached. Count each once
across durable records, LiveCore and the store fallback. This preserves the
existing budget contract during restart; the broader two-game cap work is US-007.

### Both tokens, dust and clocks

Keep the complete YES/NO inventory in the recovery coordinator/ledger. The core
can retain its current one-position/one-SELL shape: choose the larger sellable
holding (YES on tie), drain it, verify again, then select the other token. Retain
an existing selected token while its SELL outcome is unresolved. Do not sum tokens
or discard the unselected balance. Disable/delegate the current min-size-based
`_position_mismatch` heuristic during recovery so it cannot undo this selection.

Real sub-minimum holdings remain inventory, including 3.18 shares under a 5-share
minimum. They never reopen BUY or cause sub-minimum SELL. Preserve the existing
explicit sub-share-tick residue convention; do not expand it into dust write-off.
Switching to another sellable token must retain the first token’s dust in the ledger.

Never restore old monotonic nanoseconds verbatim. Persist wall timestamps plus the
remaining delay at checkpoint; rebase using elapsed wall time. If time goes
backwards, conservatively retain the remaining delay. A newly received BUY fill
during recovery restarts settle using receipt order. Books, signal freshness and
permissions must be refreshed; old model timestamps cannot authorize an exit.

The operator-facing surface is existing logs: one transition/block reason with
condition/session identity, remaining orders, unsettled fill count and both token
quantities. Emit changes, not the same warning every tick. Keep journal v6 intact
and do not create a decision-trace archive here.

## 5. Backtest integration and implementation order

Add named adapter methods to begin recovery and accept a verified recovery
snapshot. They synchronize adapter inputs, construct the shared events, execute
their plans and maintain the Nautilus compatibility state. Add RecoveryVerified
to the requote set. The synthetic driver must call these methods rather than
private `_drive(Recovery(...))` injection. Normal historical runs do not invent
restart events and retain extraction timing.

Implement in these slices:

1. Persistence schema, typed codec, independent outbox cursor and reopen tests.
2. Core recovery barrier and verified event, with pure transition tests.
3. Durable plan/outcome execution, pre-POST signed identity and unsent-command handling.
4. Boot classification/coordinator and ledger-core consumer wiring. Replace the
   old resume heuristic only after the new entry point is connected.
5. Backtest entry points and shared tape legs, then the process-crash fixtures.
6. Run the acceptance checks below and record results against this step.

Do not broaden the US-005 state-normalizer exclusion list to hide recovery
differences. Compare the new flags, generation, inventory selection, order
ownership, reserves and commands explicitly. The existing status exclusion means
timeout/unknown retention also needs direct assertions on each adapter.
