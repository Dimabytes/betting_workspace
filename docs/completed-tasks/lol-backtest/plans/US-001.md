`plan_downloads` (keep the name):

1. Same market filters as today: missing catalog → one miss row `channel=""` reason `missing_from_catalog`; token mismatch → `channel=""` reason `token_id_mismatch`. These still fail the run.
2. For each of `CHANNELS`, expand that channel's `[from, to)`.
3. Empty window:
   - required channel → miss row with that `channel`, reason `missing_interval`, `complete=False` → fail run.
   - optional channel → miss row with `channel="onchain_fills"`, reason `missing_interval`, `complete=False`, **does not fail the run**.
4. Jobs: both catalog tokens, each day, dedup key `(channel, asset_id, date)`. `condition_id` on the job is the first included market that produced it (same as books today).
5. Iterate `CHANNELS` then tokens then days so the planned tuple is books, then trades, then onchain. One thread pool still runs them concurrently — do not add three serial pools. The design's "then download trades, then onchain" is skip/download priority for a rerun, not a barrier.

If books window is empty and trades window is not: required books miss fails the run; still plan trades/onchain jobs (independent jobs continue, same as 404 siblings today).

**Skip rule (all channels):** if `validate_target` on the final path is valid, reason `skipped_valid`, no HTTP. First rerun on the existing LoL book archive: books skip, trades and onchain download. Second rerun: all three skip when valid. "Skip only verified books" in the spec is that first-rerun story, not "never skip trades".

Invalid existing file (truncated, wrong columns, wrong `asset_id`) is not skipped — redownload. Same as today's book test.

Do not rewrite or transcode provider bytes.

### 3.5 Failure policy

| Event | Audit `complete` | Exit 1? |
|---|---|---|
| required job `downloaded` / `skipped_valid` | True | no |
| required job `http_404` / `retries_exhausted` | False | **yes** |
| required channel empty catalog window | False | **yes** |
| market `missing_from_catalog` / `token_id_mismatch` | False | **yes** |
| optional `onchain_fills` `http_404` / `retries_exhausted` / empty window | False (gap in audit) | **no**, if every required row is complete |
| optional success `downloaded` / `skipped_valid` | True | no |
| HTTP 401/403 | no audit file | abort `FatalDownloadError` (not typer 1) |
| missing `TELONEX_API_KEY` | no HTTP | `RuntimeError` |

Replace `if any(not row["complete"])` with: incomplete **required** rows fail. A row is required when `channel` in `REQUIRED_CHANNELS` or `channel == ""` (market-level miss). Optional incomplete rows are printed and stored, then the process returns 0.

"Accept missing onchain_fills when trades exist" is this exit rule, not a per-token cross-check. Do not add a join that requires a trades file before recording an onchain 404. Independent jobs continue after 404 as they do today.
