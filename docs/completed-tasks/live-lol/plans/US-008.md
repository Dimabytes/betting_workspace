## 2. Current vs target

### 2.1 Why `env_file: .env` cannot stay

Compose `env_file` injects **every** key into the container. Today that includes `PK`, `BROWSER_ADDRESS`, `LIVE_TRADING`, collect tokens (`STRATZ_TOKEN`, `OPENDOTA_API_KEY`, `GRID_GG_TOKEN`, `TELONEX_API_KEY`), and Kalshi demo keys.

If `trader-paper` keeps `env_file: .env`:

1. `docker compose config` shows `PK` / `BROWSER_ADDRESS` on paper → story fails.
2. After US-015 recreate, Python `env_value("PK")` succeeds in the paper process even though it never needs a CLOB wallet.
3. `LIVE_TRADING=1` is injected → `reject_legacy_env` kills **both** new processes until `.env` is edited (US-015). Dropping `env_file` is what makes a file-only compose fail-closed on legacy env.

Project-directory `.env` is **still** used by Compose for `${VAR}` interpolation. That is not `env_file`. Interpolation does not dump unlisted keys into the container.

**Do not** use `env_file` on either service. List every injected key under `environment:`.

### 2.2 Environment lists

Compose-owned literals (same on both; match the volume mounts):

```yaml

LOL_ARCHIVE_ROOT: /archive/lol
```

Do **not** set `ARCHIVE_ROOT`. The old `/archive` mount goes away. US-010 reads the per-game vars. A stray recreate before US-010 will fail `load_archive_root()` — fail-closed, same family as missing `--mode`.

Interpolated, **no `:-` defaults** for modes (host `.env` does not have them yet; empty → `assigned_games` startup error; safer than defaulting to `live`):
