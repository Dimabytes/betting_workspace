### 2.3 `match.json` schema 5 — write `game`, do not upgrade leftovers

```text
MATCH_META_SCHEMA_VERSION = 5
ACCEPTED_MATCH_META_SCHEMA_VERSIONS = frozenset({3, 4, 5})
```

Key sets (exact keys, same style as today):

```text
_MATCH_META_KEYS_V3   # unchanged, 18 keys, no kalshi, no game
_MATCH_META_KEYS_V4 = _MATCH_META_KEYS_V3 | {"kalshi"}
_MATCH_META_KEYS     = _MATCH_META_KEYS_V4 | {"game"}   # current write set
```

Rename today's `_MATCH_META_KEYS` (v3 ∪ kalshi) to `_MATCH_META_KEYS_V4`. Keep `_MATCH_META_KEYS` as the **current write** set so `_build_start_document` stays one assignment.

Parse (`_parse_meta_document`):

```text
if schema_version == 3: expected = V3
elif schema_version == 4: expected = V4
else: expected = current write keys   # 5, already in ACCEPTED
```

Then:

- schema != 3 → parse `kalshi` (today this is `== 4` only; 5 must parse kalshi too).
- schema == 5 → parse `game` via `require_nonempty_str`; reject if `game not in GAME_PROFILES`.
- schema 3 and 4 → **do not put `game` on the parsed dict**.

`MatchMeta.game` is `NotRequired[str]`. Docstring: schema 5 requires it; 3/4 omit it.

**Why not inject `game="dota"` into the parsed dict for v3/v4:** `finalize_match`, `pin_horn_from_event`, and `update_kalshi_binding` write that dict back. Injecting `game` while leaving `schema_version` 3/4 would fail `require_exact_keys` on the next read (extra key). Bumping version on those writes would silently upgrade leftovers. The story is read-default, not a converter.

Default lives **only** in `_match_start_from_document`:

```python
game = document.get("game")
if game is None:
    game = "dota"
```

Then `MatchStart(..., game=game)`. A leftover v3/v4 file plus `build_match_start()` (game=`dota`) still compares equal → `write_match_start` no-ops and does not rewrite. Existing `test_schema_3_unfinished_resume_does_not_rewrite` stays the Dota backward-compat gate once `build_match_start` has `game="dota"`.

Schema 4 **with** a `game` key is invalid (exact keys). Defaulting is only for **absent** `game`.

### 2.4 Kalshi helpers must treat schema 5 like schema 4

Today both of these are `schema_version == 4` / `!= 4`:

- `kalshi_reason_from_document` — any non-4 is `"off"`. After the bump, **every new match would look Kalshi-off**.
- `update_kalshi_binding` — refuses non-4. **Every new match would refuse ticker bind.**

Invariant that actually matches v3: schema 3 has no `kalshi` key; 4+ do.

```python
# kalshi_reason_from_document
kalshi = document.get("kalshi")
if kalshi is None:
    return "off"
return kalshi["reason"]
```

```python
# update_kalshi_binding
if "kalshi" not in document:
    raise ValueError(
        f"match {match_id!r} schema_version {document['schema_version']} has no kalshi object; "
        "refusing to introduce a Kalshi venue"
    )
```

Update `test_update_kalshi_binding_rejects_schema_3` (`match="not 4"` → `match="no kalshi"`).

`read_kalshi_block` already uses `.get("kalshi")`. Docstring: schema 4+, not “schema-4 only”.

Boot scan (`read_finalized_match`) only checks `ACCEPTED`. **Must include 5** or every new finalized match is a foreign schema and leftover-cancel skips it. Do not require `game` on the narrow boot-scan parse. Keep `test_boot_scan_accepts_schema_4`. Add a sibling for schema 5 (writer-produced or a narrow document like the schema-4 test).
